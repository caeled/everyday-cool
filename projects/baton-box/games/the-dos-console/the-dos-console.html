The DOS Console — how it works

This page is a working DOS PC, emulated in your browser. The engine is DOSBox (GPL version 2), running through the js-dos player (also GPL-2.0) — the same pairing that serves DOS games to the whole internet at dos.zone. Both are embedded unmodified; their licenses ride with this page (see the lesson for the receipts). What the page deliberately does not contain is a single game or a single byte of DOS software. The console ships empty, the way the real one did: you bring the software.

It runs anywhere this page can stand — a plain static host, a lone saved file, the Everyday Cool app. No special server, no special headers, nothing to install. (An earlier engine needed all of that; the lesson tells that story.)

Door one — Mount your C:

  • This is the door for a whole DOS archive kept the way DOS people keep one: one folder that is a C: drive. Pick the folder itself — the DOSBox way, no zip needed — or zip that folder (right-click it, Send to → Compressed (zipped) folder) and pick the zip. Both keys open the same door.
  • The console mounts the zip as drive C: and boots to a real DOS prompt, C:\>. No auto-run, nothing launched for you. DIR, CD, and typing a program's name work the way they did in 1990, because it is DOS in there.
  • How it works, honestly: the folder key starts the machine empty and copies your files in one by one — nothing is ever held all at once, so a drive of any size your machine's memory can hold will ride. The zip key builds one package — a bundle: your files plus one small boot file, .jsdos/dosbox.conf, which this page writes for you in your browser. Either way the first commands mount the drive as C: and hand you the prompt. Nothing is uploaded. Everything happens on your machine and never leaves it.
  • The lazy drive: pick a big folder and the folder key loads its skeleton first — every folder, and every file up to 256 KB — so the prompt and the whole directory tree are yours in seconds. The big folders wait in a panel under the screen with their true sizes; load one when you want it and it streams in, the way DOS read a disk: on demand. Until a folder is loaded, DOS sees it as empty — the panel, not the DIR, is the truth about what is in. Loads are counted as they go: the panel shows how much of the drive is in the machine, and a load that would push the total past about 1.5 GB stops and says why before it starts — past roughly 2 GB the emulator can die silently, which reads as a freeze. Nothing is blocked; the load just asks once.
  • A zip has to fit in one piece in the browser — about 2 GB is the ceiling, and that limit is the browser's, not this page's. The folder has no such ceiling: when an archive outgrows zips, pick the folder. The console's zip tools are small, though: plain .zip only — no ZIP64, no password-protected entries. The status line will tell you in plain words if a zip can't ride.

Door two — one game, straight in

  • Pick a game zip and the console looks inside it for programs (.EXE, .COM, .BAT) and suggests the likely one in the Run command field. Confirm it, or type your own — the command runs exactly as typed, from C:\. If the suggestion points into a folder, the console steps into that folder first, the way you would.
  • If a game can't find its own files when run this way, it wants to be run from inside its folder — that's what door one is for: mount the drive, CD in, and run it at the prompt.

Door three — the public shelf (the Internet Archive)

  • The button opens The Oregon Trail (1990) — and the field under it opens any other item — in the Internet Archive's own player, in a new tab. The shelf is theirs, and for now the books are read in their house: the Archive's file servers don't currently give web pages permission to fetch the software itself, so no page — this one included — can honestly load it from there directly. The day the Archive opens those headers, this same door becomes a load-here door with no redesign. The lesson carries the evidence.
  • What the console can do with the Archive today: look the item up (their catalogue answers pages like this one freely), confirm it's really there, and take you straight to it.

Door four — Rescue files

  • Mount a drive, then List what's on the drive: the console reads the mounted drive's own directory and shows every file with its size. Tick the files you want, filter the list by folder or file type if the drive is big, and Download the ticked files as a zip — the console reads them out of the machine and builds the zip in your browser. Nothing is uploaded; the zip lands in your downloads like any file.
  • The field use: a folder copied off a real machine's C: drive — through a USB adapter, off a disk that still spins — mounts here, and its data can be opened by the very programs that wrote it, then carried out through this door. That is the support bench's reading room. A physically dying disk needs its imaging step (ddrescue and friends) before the console ever sees it; this door rescues files from a readable copy, it does not resurrect hardware.
  • The list shows what is in the machine right now — with a lazy drive, a file still waiting in the panel is not rescuable until its folder is loaded. Load the folder, then list again.
  • A rescue set is a handful of files, not the whole drive — the zip is built in the browser's memory, so keep a set modest and make several trips for a big haul.

Saves

  • The player's own side bar carries a save button (the floppy disk) — it keeps the machine's state and your drive's changes with the bundle, on this machine, in this browser. No codes to copy, nothing to paste: saving is the machine's job, not yours.
  • Your original folder or zip on disk is never touched either way.

Window size, fullscreen, pop out

  • Standard / Large / Extra large resize the window the DOS screen lives in; the emulator follows the box. Fullscreen gives the machine the whole display. Pop out lifts the running machine into a full-window view of its own — the same session, still running, nothing restarted — and Pop back in (or the Esc key) sets it back into the page.

Keyboard

  • DOS reads your real keyboard. Click the DOS screen once so it has focus, then type — letters, numbers, Enter, Backspace, the arrow keys, the F-keys and Esc go to DOS the way they did on the real machine. There's no gamepad translation layer to learn; a DOS machine is a keyboard machine.
  • The player's own side bar (the icons along the screen's edge) is js-dos furniture: save, an on-screen keyboard, fullscreen, turbo and settings — it all works, and it's upstream's, unmodified.

The fine print

  • No DOS software is included, hosted, or downloaded by this page's local doors — by design, and permanently. Your archive is read from your machine only.
  • Changes you make at the DOS prompt (a saved game, a high-score file) live in the machine's memory for the session. This page does not write back into your zip — download a fresh copy of your drive from your own folder when you want one; the zip on your disk is never touched.
  • “DOSBox” and “DOSBox Pure” are the names of their projects; “The Oregon Trail” belongs to its publisher. All are used descriptively — this is a fan-made console page for running your own software.

🗄️ Mount your C:

Your whole DOS archive, the way you already keep it: one mountable folder that is a C: drive. Zip the folder, pick the zip, and the machine boots to a DOS prompt — C:\> — with your drive mounted. DIR is yours from there. Nothing auto-runs; a drive is not a game.

no drive mounted

Before you pick: With a larger drive start up may take a minute or two, and you may get a browser message about uploading a lot of files. What it is doing is uploading the directory into the VM that runs the emulator. No files are copied off your machine — the emulator runs in this page, and the folder on your disk is never touched.

The folder door is the DOSBox way: pick the drive folder itself, no zip. The console streams its files into the machine here in your browser — the skeleton first, the big folders on demand — nothing leaves your machine, and the folder on your disk is never touched.

🧰 Rescue files — copy them back out

The drive you mount may be a copy of a real machine's C: — an old disk read through an adapter, kept as a folder. This door is the way back: list what is on the mounted drive, tick the files you need, and the console reads them out and hands them to you as a zip in your downloads. The original software stays the reader; this door is the carrying case. It rescues files from a readable copy — a physically dying disk still needs its imaging step first.
