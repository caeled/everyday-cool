Everyday Math · The lesson behind Warp

Warp: the picture never moves — the colours do

Warp is a tribute to Acidwarp, the 1992–93 DOS screen saver by Noah Spurrier and Mark Bilk that filled a generation of screens with swirling colour. Its entire trick fits in one sentence: compute one still picture of palette indexes, then rotate the palette — the picture is never redrawn, and the motion is free.

Written by Steven Powell in Python (his Bordeom workshop); web port by Muse, maths carried over line for line. The original runs on numpy and pygame; this page runs the same code in your browser, and the proof table below is the original's own self-test, run against the shipped code.

Indexed colour: a paint-by-numbers picture

On a 1993 VGA card, a 320×200 screen in "Mode 13h" did not store a colour per pixel. It stored one byte per pixel — an index from 0 to 255 — and a separate table, the palette, said which RGB colour each index currently meant. Warp keeps exactly that architecture. Each pattern is a pure function from pixel coordinates to an index:

index(x, y) = pattern(x, y)  ·  coordinates measured in classic 320×200 units

The nine patterns are small pieces of honest maths. Rings is just distance from a centre. Spiral adds the angle to the radius. Waves adds two sines. Plasma sums four sines at different scales — the demoscene's favourite. Kaleido folds the angle into twelve identical wedges. Interference multiplies two ripple fields. Tunnel divides by the radius, so rings rush inward. Warp pushes the coordinates through two sine fields before measuring the radius — a domain warp. Julia is a real escape-time fractal, the same iteration as Fractal's, with its smooth count stretched across the palette. Two helpers do the bookkeeping: norm stretches any field so its minimum is 0 and its maximum is 255 (times a band count), and to_index floors and wraps a float field into bytes.

Palette rotation: animation at zero cost

Once the index picture exists, animation costs nothing. Each frame the page adds a constant to every palette lookup — index i shows the colour that index i+1 showed last frame — and the whole picture appears to flow, pulse and crawl while not a single pixel value changes. On the original hardware this was done by rewriting the VGA palette registers, 768 bytes a frame; here it is the same idea in a lookup loop. The Warp page makes the trick visible: the palette strip under the picture carries a marker that walks along it as the colours rotate, and the See the index picture toggle (key G) shows the raw indexes in grey — hold still, utterly motionless — while the colour version beside the same data swims. That contrast is the whole lesson: the motion was never in the picture.

For the rotation to look smooth, the palette itself must loop seamlessly: the step from the last entry back to the first must be as gentle as any other step, or the picture tears once per cycle. Steven's palettes are built from cosines with whole-number frequencies, so each colour channel completes an exact number of full waves across the 256 entries and the wrap is automatic. The self-test measures it: for the four smooth palettes (COSINE, RAINBOW, FIRE, DUOTONE) the biggest single-channel step anywhere, wrap included, must stay under 60. BANDED is exempt on purpose — its hard stripes are the joke, very 1993.

The distinct-index counts and the exact wrap steps depend on which random palette and pattern parameters a given seed deals — the Python's own self-test run reported INTERFERENCE at 252 distinct indexes and a DUOTONE wrap step of 9, this port's run reported 256 and 3. The checks are the same; the dice landed differently. What does not vary is the shape of every claim: full pictures, seamless loops, deterministic seeds.

The honest notes. Palette rotation is a 1992–93 technique — it belongs to the era when redrawing a screen was expensive and rewriting 768 palette bytes was not. Modern machines redraw everything every frame without noticing, which is exactly why the trick is worth preserving: it is a reminder that "animation" is a property of the mapping, not the picture. Two porting differences, named plainly. First, the random generator: the Python uses random.Random (Mersenne Twister); the port uses a small mulberry32 generator. It honours the property the original relies on — same seed, same picture, proven above — but it is a different stream, so seed 7 here is not seed 7 in Python. Second, precision: the Python computes its pattern grids in float32; the port computes in float64, JavaScript's only float. An index at a knife-edge boundary can differ by one between the two; nothing else moves. And one deliberate addition: the Python original has no grey index view and no palette strip — those are the port's, added so the trick can be seen, and they change no pattern, palette or index.
