Pathfinder Arena — the lesson

Pathfinder is a racing arena for the classic shortest-path algorithms. On a 39 × 25 grid of open ground, walls, and mud that costs 5× to cross, five engines — A*, Dijkstra, BFS, Greedy Best-First, and Bidirectional A* — hunt from S to G while a telemetry card counts the nodes each one expands and the cost of the path it brings home. A second room, the Network Lab, runs Kruskal, Prim, Edmonds–Karp Max-Flow, and Bellman–Ford on weighted graphs. This page is the other half of the exhibit: the mathematics, and an audit that drove the shipped solvers headlessly against an independent Dijkstra and measured every claim the page makes.

Built by Google Antigravity (Gemini) at Steven Powell's direction; lesson and audit by Muse.

Open Pathfinder Arena →

Verdict: the core is honest and unusually good — in ordinary 4-way mode, A* and Dijkstra returned the provably optimal cost on every grid the audit threw at them, and the displayed path costs are recomputed from the real terrain, not taken from the search's own bookkeeping. But two things on the page are not true as shipped: the page's own start-up sequence throws an error before its opening terrain and animation ever load, and two of the five grid engines quietly return suboptimal paths in setups the page itself offers — Bidirectional A* even at factory settings, and plain A* the moment you pair its default Manhattan heuristic with the diagonal-movement toggle. Both are flagged in red below, with numbers.

FALSE / BROKEN 1 — the page does not finish starting up. On first load the start-up sequence loads the Network Lab preset before it generates the grid terrain. Loading a preset refreshes the telemetry, and the telemetry code reads the grid solver — which does not exist yet (gridState.solverMain is still null). The audit reproduced the exact error headlessly: “Cannot read properties of null (reading 'visitedCount')”. An uncaught error stops the rest of the start-up sequence, so the Diagonal Spiral terrain the page is supposed to open with is never generated and the animation loop is never started. The controls are wired up (they were registered earlier), so the arena can be coaxed to life by clicking a terrain generator — but as shipped, the “Ready” pill on first load is announcing a page that crashed on its way in. Fixed on 25 November 2026, under Steven's sanction (his green light on the whole Bench board): updateTelemetry now returns early when no solver exists yet, so the preset load can no longer kill the start-up sequence. Verified headlessly against the shipped page: the exact error above reproduced on the original file, and the fixed page loads with zero exceptions while its telemetry populates and the arena starts. FALSE 2 — Bidirectional A* is not optimal, even at default settings. It stops the instant the forward and backward searches first touch, and takes that meeting point as the answer. The solver even carries a field for tracking the best meeting cost — bestMeetCost — which is set to Infinity at birth and never used again. Measured: on a mud patch where the optimum is 48, Bidirectional A* brought home 52; across 30 random 4-way grids it was suboptimal on 10; across 60 random diagonal grids it was suboptimal on 29–32 of 60, depending on heuristic. First touch is not cheapest touch, and no label on the page warns you.

FALSE 3 — “A* guarantees the exact shortest path” fails in a combination the page itself offers. The guarantee needs an admissible heuristic — one that never overestimates. The default heuristic is Manhattan distance, which is admissible for 4-way movement. But the page also offers an “Allow 8-Way Diagonals (√2 cost)” toggle, and with diagonal movement Manhattan overestimates: by up to 7.03 on this grid (it charges 47 for a journey that diagonals complete for 39.97). Nothing warns you when you combine them. Measured across 60 random diagonal grids: A* + Manhattan was suboptimal on 33; A* + Euclidean and A* + Octile — both genuinely admissible with diagonals — were suboptimal on 0. The fix is one sentence of labelling, or auto-switching the heuristic when diagonals are switched on.

The mathematics

One question, five temperaments

Every grid engine answers the same question — cheapest route from S to G, where entering a mud cell costs 5 and everything else costs 1 — and they differ only in what they look at next:

f(n) = g(n) + w · h(n) g(n) is the true cost already paid to reach a cell. h(n) is a guess at the cost still to come. Dijkstra is the case h = 0: trust only what you've paid, expand in every direction. Greedy Best-First is the opposite: trust only the guess, sprint at the goal. A* adds them, and when w = 1 and the guess never overestimates (admissible), the first time A* reaches the goal it holds a provably cheapest path — while usually expanding far fewer cells than Dijkstra, because the guess steers it. BFS ignores cost altogether and counts hops. Bidirectional A* runs A* from both ends at once.

The heuristic is where movement rules and arithmetic meet. For 4-way movement, Manhattan distance (|dx| + |dy|) is the exact cost on empty ground, so it can never overestimate on a map whose cheapest step is 1 — mud only makes real journeys dearer, which keeps the guess safely low. Allow diagonals at √2 and the exact empty-ground cost becomes the Octile distance; Manhattan now overestimates, because it charges full price for travel that a diagonal does at a discount. Euclidean distance (the straight-line √) never overestimates either movement style. The audit measured all three against the true diagonal cost, cell by cell — see Receipt 3.

Why “first meeting” is not “best meeting”

Two searches rushing at each other will touch somewhere. The cheapest route through their shared territory may cross at a different cell than the first one they both happen to visit, and a correct bidirectional search must keep going until it can prove no cheaper crossing remains — tracking the best complete S→G cost found so far and stopping only when neither frontier can beat it. Pathfinder's Bidirectional A* stops at the first touch instead. On open ground, where the two cones meet head-on along the optimal corridor, that shortcut is invisible. Around mud and walls it costs real money, as the receipts show.

The audit — claims checked against the shipped code, with receipts

The audit extracted the exhibit's own script and ran it headlessly in Node with DOM and canvas stubs — the shipped createGridSolver / stepGridSolver functions themselves, stepped to completion, on grids the audit built in the exhibit's own state. Every returned path was checked three ways: the path is legal (starts at S, ends at G, moves to neighbouring cells, never crosses a wall), its cost was recomputed from the terrain, and that cost was compared against an independent Dijkstra solver written for the audit, implementing the same movement and terrain rules (including the exhibit's corner-cutting rule: a diagonal is blocked only when both orthogonal neighbours are walls). No claim below rests on reading the code alone.

Receipt 6: the Network Lab spot-checks pass

The audit's remit was the grid, but the Network Lab's engines were run too, as a spot check. Kruskal and Prim — two independent constructions of a minimum spanning tree — agreed on total weight on all four presets (City Fiber 54, MST Mesh 36, Max-Flow Pipes 34, Negative-Weight −2), and the audit's own hand-rolled Kruskal reproduced the Fiber figure of 54 exactly. Edmonds–Karp reported a max flow of 27 on the pipeline preset, which is provably optimal there: the three pipes into the sink carry 9 + 8 + 10 = 27 in total, so nothing can do better, and it found all 27. Bellman–Ford ran the negative-weight preset without flagging a cycle, and after the page's own “Inject Negative-Weight Cycle” button was driven, it flagged the cycle correctly.

Simplifications and bends, named

“Speedup vs Dijk” is a node count, not a clock. The number is baseline Dijkstra expansions ÷ this engine's expansions (open grid: 720 ÷ 33 = 21.82×). That's a fair and useful comparison — expansions are the honest currency of search — but it is labelled “speedup,” and no wall-clock time is measured anywhere. In race mode, mid-race, the figure is computed against the finished baseline count while the race's own Dijkstra is still running, so the live number is really “final Dijkstra vs A* so far” — it only becomes a like-for-like ratio when both finish.

“Shrinking the search area roughly in half” — not measured, and often not true. Bidirectional A*'s theory note promises roughly half the area. Measured visits against plain A* on the same maps: open grid 33 vs 33 (no saving — A* was already a laser), mud patch 267 vs 313 (a modest saving, for a worse path), concave trap 611 vs 490 — the bidirectional search expanded more than the one-way search it is supposed to halve.

BFS counts diagonals as hops of 1. Internally, BFS advances its distance counter by 1 for every step, diagonal or not, mud or not — correct for hop-count, and the reason its diagonal-mode results stray so far from weighted-optimal (46 of 60). The displayed path cost is still the true terrain cost, recomputed step by step — the exhibit gets credit for showing the unflattering number.

Small print: the telemetry card's fourth tile is labelled “Optimal Length” in the page's static HTML and silently relabelled “Path Length” by the telemetry code — the second is the honest label, since (per False 2 and 3) the length shown is not always the optimal one. Scores are stored in 32-bit floats, which costs nothing at these magnitudes. And there is no plain DFS among the grid engines — depth-first search appears only behind the scenes, as the Recursive Backtracker that generates the maze preset (its button says so).

What the page gets right, on the record: Dijkstra described as “A* with h = 0” — exactly true, and the code literally implements it that way. The mud warning in the BFS note — measured true. The Greedy warning — measured true. Path costs recomputed from terrain rather than trusted from search bookkeeping — the single best honesty decision in the build, and the reason every suboptimal result above is visible in the page's own numbers if you run a baseline beside it.
