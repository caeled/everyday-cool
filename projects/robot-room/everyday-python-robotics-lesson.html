Everyday Python Robotics — the lesson

Strip every robot program ever written down to its skeleton and the same three bones remain: sense, decide, act — read the world, choose, move — inside a loop that never ends. The bench beside this page hands you that skeleton in a small, real dialect of Python and a robot that obeys it exactly: no canned animation, no pretend execution. This page is the other half: what the loop is, how the page can honestly claim to run your code, how the robot moves, and the receipts from driving all of it before it shipped.

The loop is the program

A robot that drives open-loop — "motors on, wait two seconds, motors off" — is guessing. The battery sags, a wheel slips, the floor tilts, and the guess lands in the furniture. Every working robot program therefore has the same shape, from a £30 buggy to a Mars rover:

while True:
    reading = read a sensor        # SENSE
    if reading says act:           # DECIDE
        command the motors         # ACT

The three missions on the bench are that shape at three sizes. Mission 1 is the loop with one sensor and one decision: while there is room, drive. Mission 2 makes the decision three-way — left sensor winning, right sensor winning, or a tie — and the action becomes steering. Mission 3 is the honest admission that one sensor can't do everything: where sensing runs out, the program counts time instead, spinning for a counted number of ticks. Real robot code is these three moves, composed deeper.

The four functions are the whole robot

read_distance() casts a ray from the robot's centre along its heading and returns the distance to the nearest wall face or table edge — the page computes it against the world's actual geometry, and the proofs below check it against both closed-form answers and an independent step-by-step ray-march. read_light() returns a two-item list, [left, right], from sensors mounted 18 units ahead of the centre and 14 to each side: 100 directly over the dark line's centre, falling by 4 per unit past its edge to 0. set_motors(left, right) sets wheel speeds (clamped to ±200) and — this is the part beginners trip on in real code too — lets time pass: one tick, 0.05 s, per call. stop() zeroes the wheels and also passes a tick. A loop that reads sensors but never commands the motors never advances time, so the robot sits frozen mid-thought. That is not a quirk of the page; it is what happens on real hardware when the motor call is never reached.

How the robot moves — differential drive

Two wheels on one axle, driven independently, is how almost every small robot on Earth moves. The arithmetic is two lines:

v = (left + right) / 2   ·   ω = (left − right) / track Forward speed v is the average of the wheel speeds. Turn rate ω is their difference divided by the track — the distance between the wheels, 40 units on this bench. Equal wheels: ω = 0 and the robot goes straight. Opposite wheels: v = 0 and it spins in place. One wheel faster: it arcs toward the slower side. (The bench works in screen coordinates, where y grows downward, so its ω is signed for the screen: a faster left wheel veers the robot right, exactly as a real robot veers away from its faster wheel.)

Each tick the page integrates one step — heading first, then position along the new heading — and refuses any move that would put the robot's body inside a wall, letting it scrape along instead. The proofs below spin the robot with opposed wheels for 10 ticks and check the heading changed by exactly −2.000 rad with the position unmoved to the last decimal: the model does precisely what the formulas say, no more and no less.

The interpreter, named truthfully

The honesty box: the bench does not contain Python. It contains a small interpreter for a beginner subset of Python, written in JavaScript for this page — a tokeniser, a parser, and a tree-walking executor, about the size of a good weekend project. It is not CPython, and it does not pretend to be: the subset is variables, arithmetic (/ true division, // floor division, % with Python's sign rules — chosen to match real Python 3, not JavaScript), comparisons, and/or/not, if/elif/else, while, break, pass, lists and indexing, and comments. There is no def, no for, no strings, no imports, no print — the robot and its readouts are the output. Use one of the missing pieces and the page tells you, with the line number, that it is outside the subset.

Why it must work this way: a web page cannot safely run arbitrary visitor code — real Python handed a stranger's program would be a security hole with a steering wheel. A small interpreter that knows exactly four functions and nothing else is safe by construction: there is no file access, no network, no system call in its world to abuse. The same reasoning gives the step cap: 2,000 statements per run, counted one per executed statement. A runaway while on the bench stops with a clear message at exactly step 2,000 — the proofs trip it deliberately — instead of hanging the page. On a real robot the equivalent safety is a watchdog timer, and it exists for the same reason.

What transfers: everything except the subset's edges. The loop shape, the indentation, the operators and the control flow are real Python; the same program, with read_distance swapped for an ultrasonic sensor's driver call, is recognisably the program a MicroPython board runs. The references below are the doors from this dialect to the full language and to real hardware.

The missions, read as lessons

Mission 1 teaches threshold thinking: a sensor reading is useless until it meets a number. The starter stops with 60 units to spare — change the 60 and you change the robot's nerve. Mission 2 teaches differential sensing: neither light sensor alone knows where the line is, but their difference is a steering signal — steer toward the side that sees more. This bang-bang controller (full correction, either way, no in-between) is the ancestor of the proportional control in the Robot Room's Control workshop. The bench grades it honestly: it tracks what fraction of the trip the robot's centre spent within the line's band and demands 60%. Mission 3 teaches the limits of both: with no sideways sensor, the program navigates the box by dead reckoning — counted ticks of spin and drive — which works precisely because the simulated world is exact, and drifts on real robots for the reasons the dead-reckoning reference below describes.

Honest bends

Perfect sensors, perfect wheels. Readings here have no noise, no flicker and no lag, and motors reach commanded speed instantly. Real light sensors chatter at the line's edge — which is why real line-followers add hysteresis or proportional steering — and real motors spool up over tens of milliseconds. The bench's bang-bang follower would jitter on hardware; its logic would still be right.

Distance is measured from the centre. A real ultrasonic sensor sits on the robot's nose and reads from there; this page reads from the centre for cleaner geometry, and says so in its Help. Thresholds you tune here would shift by roughly a body radius on hardware.

Time is discrete and honest about it. Robot time advances only on motor calls, in exact 0.05 s ticks. Real loops run on a clock whether the code is ready or not — code that computes too long misses its slot. The bench's model is the kinder, teachable version of the same fact.

The subset's edges are real edges. No for loops (a counted while does the same work here), no functions of your own, no strings, no print. Each absence is a deliberate trade for an interpreter small enough to be safe and to explain on one page — and each is a reason the references below exist.
