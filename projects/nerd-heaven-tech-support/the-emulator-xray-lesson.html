Emulator X-Ray — the lesson

Two small vector games — a Lunar Lander and an Asteroid Drift — wearing a layer that shows their own machinery while you play: velocity and acceleration arrows on the ship, dashed collision boundaries, a live telemetry panel, and a pause-and-step control that advances the physics exactly one tick at a time. It is not an emulator and carries no ROMs — the page says so itself, in its own footer. It is the reference exhibit for a pattern the whole shelf can borrow: play → pause → step → understand.

Where it came from

This page is a guest build: ChatGPT built it (Steven's idea, 25 November 2026 — "being able to turn on an X-Ray for some games that shows the physics"), and it joins the collection the way guest builds do: the page ships byte-for-byte as its builder wrote it, Muse's job is the audit below and this lesson. The candidates inventory for the rest of the shelf lives with this lesson's working papers.

What "X-Ray" means here

Press F2 and the game draws what it knows: a blue arrow for velocity (where you are moving), an amber arrow for acceleration (how that motion is changing), dashed outlines for the exact shapes the collision test uses, and a fading trail of the last 120 simulation positions. Below the screen, three panels read the simulation live — the actual numbers, a "what just happened?" event line, and an Explain this moment button that narrates the current tick. A mode switch re-reads the same moment three ways: Player (plain words), Programmer (the update order, and a register picture — labeled a toy, see below), Engineer (timestep, frame intervals, discarded catch-up time). Pause with P; step one 1/60-second physics tick with N; restart with R.

input → acceleration → velocity += acceleration × dt → position += velocity × dt → collision → event The page's own printed update order (Programmer view). The audit below paced it out and it does exactly this, in this order, every tick.

The honest-instruments boundary

Real: everything about the two games themselves — motion, fuel, contacts, tick counts — is read straight out of the running simulation. The audit above compared the panel against the sim's own state variables and they agree exactly.

Labeled toy: the Programmer view's "registers" (A, X, Y as hex bytes) are derived from game state for teaching shape, and the page prints "ILLUSTRATIVE TOY REGISTERS — No emulated CPU. No real register telemetry" right on top of them. There is no CPU in this page, and it never pretends otherwise.

Unavailable, and named unavailable: hardware registers, scanlines, bus activity, CPU cycles — the Engineer panel lists them as not emulated rather than inventing numbers. That honesty is the house rule for every X-Ray that follows: real where the machine is ours, labeled where it is a model, silent where it would be theater.

Bends and reading notes

  • The mission line at the top of the Lander screen says "PAD 420–580" — that's the painted line. The verdict quietly requires the ship's centre inside 432–568 so the whole ship is over the pad. Consistent, and the Player panel explains it, but a player reading only the mission line could feel cheated by a 431 landing. Noted, not changed — the page ships as built.
  • Step (N) steps a physics tick, not a CPU instruction — the page's Programmer panel says this in so many words. On the 6502 Bench follow-on, the same button will mean an actual instruction, because there it can.
  • The trail holds the last 120 positions as printed (audit sampled it growing 1-for-1 with ticks; the cap is in the code and the counter never exceeded it).
