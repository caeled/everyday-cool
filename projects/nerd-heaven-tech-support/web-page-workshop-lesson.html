What WYSIWYG means

WYSIWYG — "what you see is what you get," pronounced wizzy-wig — is the deal the white sheet makes with you: the page you are editing is the page, not a picture of it. When you make a word bold on the sheet, the word in the real page becomes bold at that same moment. There is no translation step afterwards where things can get lost, because there is nothing to translate: the editor edits the thing itself. That is why the View Source trick works — flip the sheet over and the code you see is not a description of your page. It is your page, wearing its other face.

The tool is made of the thing it teaches

Here is the part worth sitting with. The workshop is a web page. Its toolbar is HTML. Its buttons are HTML. The white sheet is an ordinary page region with one attribute — contenteditable — that tells the browser "let the visitor type in here and change things." The workshop's own View Source button and the one in your browser are cousins: open this very page's source and you can read the workshop the same way the workshop reads your page. A beginner who finishes a first page here has already been standing inside the answer to "what is a website made of" the whole time: text, tags, and a browser that obeys them.

<div contenteditable="true"> …type here… </div> That one attribute is the whole doorway. Everything else in the workshop — the toolbar, the picture inserter, the serializer — is furniture arranged around it.

View Source — why "the code is the website" is literally true

A web page is a text file. When a browser opens one, it reads the text — <h1> means a big heading, <b> means bold, <a href="…"> means a link — and paints what the text describes. The painting is a rendering of the text, the way a song is a rendering of sheet music. So when the workshop's source view shows your page's HTML, it is not showing you a blueprint of a thing that exists somewhere else. The HTML is the thing; the pretty page is just the HTML, played.

That is why the door swings both ways. The source view pretty-prints the canvas's HTML — block elements on their own lines, indented by nesting, inline elements left flowing in the text — into an ordinary text box. Edit the text, press Done, and the workshop parses your edited text back into elements and re-renders. Change a word in the code and the word changes on the page, because they were never two things.

The buttons' engine, named honestly

The honest note: the formatting buttons are powered by document.execCommand, the browser's built-in editing engine. The standards world has marked it deprecated — the official advice is "don't build new things on this" — and yet every browser still ships it, still supports it, and shows no sign of removing it, because a generation of editors was built on it. This bench uses it deliberately and says so: for a first editor, a working built-in engine that every browser honours beats a hand-rolled replacement ten times its size. If it ever does vanish, the buttons are the only part of the workshop that would need rebuilding; the canvas, the source view, the serializer and the autosave are plain DOM and would not notice.

What execCommand does with a command like bold is worth knowing: it edits the document's own structure — wrapping the selection in a <b> element — rather than painting bold-looking pixels. That is why the change shows up in View Source. The button and the code view are two handles on the same structure, which is the whole lesson of the bench in miniature.

Pictures that travel — data URLs

A normal web page does not contain its pictures. It contains an address — <img src="cat.jpg"> — and the browser goes and fetches the picture from that address. Move the page without the picture file and the page shows a hole. The workshop chooses the other trade: when you insert a picture, the browser's FileReader reads the picture's bytes and writes them into the src itself, encoded as text — a data URL. The exported file is then genuinely self-contained: one file, page and pictures together, openable anywhere forever. The cost is printed on the bench too: the file grows by roughly the picture's size (the text encoding adds about a third again), so a page full of huge photos becomes a huge file. For a first page, portability wins. For a photo archive, it wouldn't — and now the beginner knows why real sites keep pictures as separate files.

Autosave — localStorage, and its limits

Every change on the canvas fires an input event, and the workshop answers it by writing the canvas's HTML into localStorage, the browser's small built-in storage box for the site. Open the workshop tomorrow and it reads the box first: your page is where you left it. The limits are named on the bench and repeated here: the box belongs to this browser on this device — it does not follow the page to another machine, and clearing the browser's site data empties it. Autosave is a courtesy, not an archive. Export is the archive.

Preview and Export — one serializer

Both Finish buttons call the same function, which wraps the canvas's HTML in a complete document — doctype, <head> with the page title, <body> — and hands back the text. Export puts that text in a file download. Preview puts the identical text in a Blob URL and opens it, so the page stands alone in the device's default browser, chrome and all, exactly as the world will see it. Because there is one serializer and not two, the preview can never drift from the export — and the test suite below asserts byte-for-byte that it doesn't.

The safety wash, in one plain sentence

In one sentence: when code comes back from the source view, the workshop parses it into an inert document where nothing can run, strips out script elements and every event-handler attribute, and only then lets it become the page — so pasted code can change how a page looks, but it can never execute. The suite below pastes a live <script> and an onclick trap into the source view and confirms both are gone, and nothing ran, before the page re-renders.

The interaction tests — driven, not just read

Before this bench shipped, a test driver loaded the shipped page into a DOM (jsdom, under Node) and used it: it clicked the real Bold toolbar button with a real selection in place, then ran the page's own nine-interaction suite — the same suite the bench re-runs live when a visitor presses its test button. One stand-in must be named: jsdom has no execCommand, because that engine lives in real browsers, so the driver installed a minimal version of just the three primitives the assertions exercise (bold, insert-HTML, create-link) and let the page's own wiring, dialogs' logic, pretty-printer, sanitizer, serializer and autosave run exactly as shipped.
