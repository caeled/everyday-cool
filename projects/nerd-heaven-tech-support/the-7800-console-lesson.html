The 7800 Console — the lesson

Atari's 1986 machine — the 2600's bigger sibling, a 6502 heart with the MARIA graphics chip doing the drawing — emulated in one page, and, like every machine on this shelf, it ships with no games at all. What it plays is your cartridge: a .a78 from your own library, read on your machine and kept on your machine. No BIOS, no fuss — the 7800 keeps its firmware story simple, so this console is one slot and a start button. Under the hood is ProSystem, the Atari 7800 emulator by Brian Berlin and Greg Stanton, as a libretro core inside the EmulatorJS frontend — both embedded unmodified, both licenses carried with the page. This page is the receipt: where they came from, the license reasoning in plain words, and what was verified by driving the shipped page with a synthetic cartridge built for the purpose — including the two things the audit caught that a spec sheet would have got wrong.

Where this one came from

The Atari 7800 ProSystem was designed in 1983–84 by General Computer Corporation for Atari, launched briefly in 1984, then shelved during the company's sale and finally released in 1986 to fight the NES. Its party trick was MARIA, a display-list graphics chip far beyond the 2600's TIA, and its good manners were backward compatibility: it plays nearly the whole 2600 library too. (This console's slot takes 7800 cartridges; the 2600 has its own console beside it on the shelf, running Javatari.) The ProSystem emulator — no relation beyond the borrowed name — has been the reference open-source 7800 emulator for two decades, and its libretro core is what EmulatorJS packages.

What ProSystem and EmulatorJS are

ProSystem emulates the whole machine: the 6502 (a Sally 6502C, in Atari's naming), MARIA's display-list rendering, the TIA/RIOT the 7800 inherits for sound and input, and the cartridge mappers the .a78 header describes. EmulatorJS is the same frontend the SNES, DOS and MAME consoles on this shelf already carry — it loads the core, owns the screen, the save states behind the challenge baton, and the keyboard map. That shared frontend is why this console's furniture matches its siblings exactly, and why its key table still had to be measured for itself: the frontend deals in RetroPad buttons, and what each button does is the core's business, not the frontend's.

The license question, in plain words

Two licenses ride with this console, and both are carried verbatim in the rack. The frontend is GPL-3.0, the same text the sibling racks carry. The core is GPL-2.0 — ProSystem's own license. One wrinkle, recorded rather than smoothed over: the npm core package ships no license file at all (its package.json license field is literally the string “License.txt”), so the GPL-2.0 text in this rack was fetched from the core's own repository, EmulatorJS/prosystem-libretro, where License.txt sits at the root — 18,347 bytes, sha256 9fae8c2a…1b0 — and is carried byte-for-byte. No cartridge, ROM image or game data of any kind is in the rack or the page; the machine is shipped, the games are yours.

The threading verdict — this one runs on the plain site

The DOS Console beside this one is exhibit-only on the website: its core ships threaded builds only, threaded builds need cross-origin isolation, and a static host can't send the headers. This core is not in that cage, and the verdict is measured, not inferred:

  • The core package ships a non-threaded payload alongside the threaded ones, and its build report declares no options and no thread requirement.
  • The frontend's own requires-threads list, read in its shipped source, is exactly ["ppsspp", "dosbox_pure"] — this core is not on it.
  • The console page therefore never sets EJS_threads, and the audit booted it on a plain local server with window.crossOriginIsolated === false asserted in the page — no COOP/COEP headers anywhere — and played it; the server's log shows the frontend selecting prosystem-legacy-wasm.data, the non-threaded build. This console runs on GitHub Pages as Pages serves today.

The audit — a synthetic cartridge, driven through the shipped page

No commercial ROM was used, and none is kept. The audit cartridge is a synthetic .a78 built for this pass: 32 KB of hand-assembled 6502 that paints the whole screen one colour per input, so a headless drive can measure the key map at the cartridge instead of trusting any table — the standing rule since the SNES console's cross-wired first draft. A real homebrew cartridge (the Truchet tiling demo, from the public shelf) was also driven through the same page and rendered its full tile pattern, as a witness that the machine plays real cartridges, not just the fixture.

The audit's own miss, first. The fixture's first build painted a perfect black screen: it wrote MARIA's background register and waited, and MARIA, like the real chip, shows nothing until a game hands it a display list and switches its DMA on. The fixture grew a proper display list (seventeen empty zones over a one-byte end-of-list) and the colours came. The core was never wrong; the test cartridge was, and the fix is recorded here rather than tidied away.

The buttons — where the spec sheet would have lied. The first measurement said both fire keys (Z and X) fired the same button. That is not a wiring error: it is the 7800's real one-button mode, the machine's power-on default, in which either button drives the single legacy input (INPT4) — the mode 2600-style games live in. A game that wants two buttons says so by setting the RIOT's CTLSWB bit, which moves the buttons to INPT1 and INPT0 with the opposite polarity. The fixture was taught to set that bit, and the two-button map then measured cleanly, each button alone and both together. The core's own RIOT source, read during the audit, documents the same mechanism — the measurement and the source agree, and the page prints the measured table:

The rest of the receipts: the screen box is 840×630 — the core declares a 4:3 picture in its own system info, and the page's 4/3 guard matches it. A state exported mid-run came to 65,675 characters under the 7800STATE1: prefix and imported back to the same machine state. The request log for a full session shows every fetch same-origin except the one external call named in the honest notes. The file:// guard was driven as well: opened as a lone file, the page locks its slot and explains itself in plain words.

Honest notes

The one phone-home attempt. The frontend, unmodified, tries once per session to fetch a version file from cdn.emulatorjs.org. It is upstream's own update check — the sibling audits met the same call — it carries no data about the player or the cartridge, it is not needed for play, and offline it simply fails. It is named here because “zero external requests” would otherwise be a claim this page couldn't keep.

Two page errors, both upstream, neither touches play: that version check's failed fetch, and the frontend's wake-lock request, which headless browsers deny (the sibling audits met the same denial).

The sandbox runs slow. The audit's headless browser ran the emulation at a fraction of real speed — slow enough that a timed “colour parade” fixture (paint each test colour for a second in turn) couldn't be sampled reliably. The audit switched to constant-colour swatch cartridges and long key holds, which are speed-proof. On a real machine the console runs at full speed; the slowness was the test bench's, not the page's.

Player 2 is wired by the core on a second gamepad; the page's printed table is the player-1 keyboard, which is what the audit measured.

The audit's ground. Drives ran headlessly against a plain local server — Steven's environment lesson (he opens lone files and real sites, not served folders) is answered by the file:// guard being driven too, and by the live-site verification recorded in the wiring receipts. His own library remains, as ever, the final receipt: his first 7800 cartridge through this page is still his to give.
