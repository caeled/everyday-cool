Pack 001 — The Broken Boot

A lesson pack is a C: drive with a starting state: download it, mount it on the Workbench, and you are standing inside the problem. This pack is a small front-desk machine whose morning startup fails — the report program "is gone," except it isn't. The drive is the homework; this page is the bench talk that goes with it. Everything in the pack is batch files and text, written for this lesson, and the whole thing is 2.4 KB: a drive that is broken in exactly one place, on purpose.

Get set up

On the Workbench (or the DOS Console), use door one's zip key and pick the downloaded pack — it mounts as C: and you land at the prompt. Or unzip it anywhere and mount the folder; a folder you can edit is a folder you can fix in place, and remounting resets the pack to its broken state, so nothing you do can harm it. Then read the drive's own README.TXT (TYPE README.TXT) — the scenario lives on the drive, the way it would on a real machine.

The call

Every morning, the person at this desk runs one command — AUTOEXEC — which sets the machine up and prints the morning report. This morning the startup stops halfway with DOSBox's own words: Illegal command: REPORT. The report program, they will tell you, has been deleted. It has not. Your job is to prove that, find the actual fault, and leave the machine starting clean.

Work it the bench way

1. Read the error literally. Illegal command: REPORT does not say the file is gone. It says DOS was told to run REPORT and could not find a command by that name. Those are different problems, and confusing them is how a five-minute call becomes an afternoon.

2. Prove where the program is. DIR C:\TOOLS — there sits REPORT.BAT, present and correct (the drive's NOTES.TXT says it has never once been deleted). Run it by its full path, C:\TOOLS\REPORT, and the morning report prints. The program is alive. So the failure is not the program — it is the finding of it.

3. Follow the chain. TYPE START.BAT: the workday banner calls REPORT by its bare name, so DOS must find it through the PATH. TYPE AUTOEXEC.BAT: the startup sets PATH C:\;C:\TOOL. And PATH on its own prints the same thing back. The folder is called TOOLS. The path says TOOL. One letter, dropped — the classic of the genre, and invisible until you read the file instead of believing the symptom.

4. Prove the diagnosis before you repair anything. At the prompt: PATH C:\;C:\TOOLS, then START. The report prints. Diagnosis proven with the machine's own behaviour — breakage, and its absence, are the only honest audits.

The fix

The proof fixed the session; the machine needs the fix in its startup, so tomorrow morning works too. Two honest methods. The folder method: if you mounted the pack as a folder, open its AUTOEXEC.BAT in any editor on your own machine, change C:\TOOL to C:\TOOLS, save, remount, rerun AUTOEXEC. The period method: fix it inside the machine, the way it was done at the time — COPY CON AUTOEXEC.BAT, type the corrected file line by line (@ECHO OFF / PATH C:\;C:\TOOLS / CALL START.BAT), and press F6 then Enter to close it. Either way, verify like a bench tech: remount or rerun, and watch the whole workday start clean, report and all.

Now break it on purpose

The pack cannot be harmed — remounting resets it — so use it the way a bench is meant to be used: change one thing and watch what it does. Point the PATH at a folder that doesn't exist and rerun AUTOEXEC: which line fails, and what exactly does DOS say? Rename REPORT.BAT to REPORT.BAK with the PATH correct: the error returns wearing the same words — now you know those words mean "not found," whatever the cause. Move the CALL START.BAT line above the PATH line: order is a real thing in a startup file, and watching a machine fail for order alone teaches it faster than any paragraph here. That is the whole method of this room: a startup file is a small program, and small programs can be read, changed, and watched.

Why AUTOEXEC.BAT still matters

Every operating system still runs one. The names changed — AUTOEXEC.BAT became login scripts, then .bashrc and profiles, then launch agents, systemd units and container entrypoints — but the job never did: set the environment, set the search path, start the work, in that order, every time, before the human touches anything. And the failures kept their shape too. A PATH typo stopped a front desk in 1994; a PATH typo stops a build server today, with the same symptom ("command not found") and the same fix (read the file, not the panic). CONFIG.SYS belongs to the same family portrait — FILES=, BUFFERS=, DEVICE= were a machine's opening negotiations with itself — and it gets its own pack in this series, on a bootable drive image where those lines truly run. Learn to read the little file that runs first, and you can walk up to almost any machine, of any era, and start work.

What the audit drove

The shipped pack, mounted on the shipped Workbench and worked with typed commands: AUTOEXEC reproduced the fault exactly — banner, Loading the morning report program…, Illegal command: REPORT., and START's own closing line. PATH printed the typo back (PATH=C:\;C:\TOOL). The folder-method fix was applied to the mounted drive and read back byte-for-byte, and AUTOEXEC then ran the whole workday clean — the morning report printed in full. One audit note, stated plainly: the audit's injected keystrokes could not send a backslash, so the run-it-by-path step was proven by the fixed startup instead — once the PATH was right, REPORT ran by its bare name, which is the stronger proof anyway. A human keyboard sends backslashes fine. Zero page exceptions throughout.

The pack format, v1

A pack is three things: a drive folder (here, shipped as a zip with the drive's contents at its root), a README.TXT on the drive itself carrying the scenario, and a lesson page in this room carrying the bench talk. Packs ship only files that are ours or free — this one is eight small text and batch files, nothing borrowed — and a pack built around commercial software is bring-your-own-media, the same rule as every console in this room: we ship the machine and the lesson, never someone else's software.

These packs are shareware, in the old sense: if one teaches you something and you want to keep them coming, the tip jar is ko-fi.com/caeled. The same note rides inside every pack as REGISTER.TXT; it is not mentioned anywhere else.
