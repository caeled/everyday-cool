The SNES Console — the lesson

A complete Super Nintendo that runs in a web page — and ships with no games at all. The console is the exhibit; the cartridges are yours, read from your own machine and never uploaded. Under the hood is Snes9x, the long-lived SNES emulator, running inside the EmulatorJS frontend — both embedded unmodified, both licenses carried with the page. This page is the receipt: where they came from, the license reasoning in plain words, what was verified by driving the shipped page, and where the honest limits are — including one big one, measured at the cartridge, that nobody's documentation mentions. One of those “limits” — the big one — turned out to be the audit's own error, and this page corrects it in the open below, in The correction.

▶ Open The SNES Console

Where this one came from

Steven Powell's ROM library lives on a mapped drive at his house — a near-complete Atari 2600 collection, homebrew NES games, and the SNES shelf. In his words, those three consoles “constitute the bulk of my collection.” The library cannot ship: those files are his, several are other people's work, and none of them belong in a public collection. So each console in this wave splits the problem the way the original hardware did — the page ships the machine, the player brings the cartridges. The SNES is the fourth machine of the wave and the biggest: where the 2600 and the NES run on 6502-family processors, the SNES runs a 65816 — the 16-bit big sibling — and Steven commissioned it on 2026-11-24 to complete the shelf.

The SNES also arrived with the wave's only license gate. The fast, maintained cores were surveyed first; the lawful browser path turned out to be EmulatorJS with its Snes9x core, and Snes9x is not open source in the usual sense — it is freeware under its own terms (next section). Steven's ruling, given before a single file was copied: implement it with attribution — Snes9x's license text verbatim with the files, and prominent Snes9x credit on the page face and in this lesson. That ruling is the shape of everything below.

What Snes9x and EmulatorJS are

Snes9x is one of the oldest continuously developed SNES emulators — a full 65816 CPU, PPU picture chips, the SPC700/S-DSP sound pair, and support for the common cartridge enhancement chips. The build vendored here is EmulatorJS's official WebAssembly build of the Snes9x libretro core (its own build report, carried in the rack, dates it 2025-06-14). It ships as four payloads: a standard build, a legacy build for the non-WebGL2 path, and two thread builds that need SharedArrayBuffer — which needs cross-origin-isolation headers a static site like this one doesn't send. On this collection, the legacy build is the one that runs; the audit below caught it being fetched by name.

EmulatorJS (version 4.2.3) is the frontend around the core: the loader, the on-screen furniture, the controller plumbing, the state machinery. The house page does not modify any of it. It sets EmulatorJS's documented configuration globals — player element, core name snes, the cartridge as a local File object, databases off — points EJS_pathtodata at the vendored folder beside it, and appends upstream's own loader.js, exactly the boot pattern of EmulatorJS's official demo. The state baton wraps the same getState() / loadState() calls EmulatorJS's own buttons use. Everything upstream is byte-for-byte; everything house-made is in the two house pages.

The license question, in plain words

Snes9x's terms are the bar, and they are short enough to say plainly: Snes9x may be used, copied, and distributed in binary and source form for non-commercial purposes, and it is freeware for personal use only. This collection is a personal, non-commercial page; nothing is sold, nothing is charged, and the emulator is distributed whole and unmodified with its license attached — inside the terms as written. The license text rides at emulatorjs-snes/LICENSE-snes9x.txt (sha256 70efeee2…e78) and was verified byte-identical in three places: the copy in this folder, the license.txt embedded inside each core payload, and the LICENSE in the upstream Snes9x repository. That text is also where Snes9x's long roster of authors and bundled-component contributors is recorded — it governs all of them, and it travels with the files, which is what it asks.

EmulatorJS is GPL-3.0. Its license rides at emulatorjs-snes/LICENSE-emulatorjs-gpl-3.0.txt (sha256 a617fab6…a61), taken from its own npm package. The frontend is served unmodified, as its own files, from its own folder; the house console page is a separate page that configures it through its documented settings and links to it the way EmulatorJS's own demo does. Nothing upstream was edited, relicensed, or hidden — the credit block on the console's face says who made what, and this lesson is the paper trail.

Trademarks. “SNES”, “Super Nintendo” and “Super Nintendo Entertainment System” are trademarks of Nintendo. They are used here descriptively — this is a fan-made console page for playing your own cartridges — and Nintendo had nothing to do with it.

The audit — a cartridge built to be measured

An emulator's word is worth nothing until a known program produces known pixels. The audit ROM is a synthetic fixture, written for this test and not shipped anywhere on the page: a 32,768-byte LoROM cartridge (sha256 69744eb0…5fb) whose 422 bytes of hand-assembled 65816 paint a known picture — white block rows over a purple backdrop (colour $4010), a red/green checker stripe — and then watch the joypad: one branch recolours the backdrop for the A and B bits, and a rising edge of Start flips a white banner row on and off, so a saved moment can be seen to come back. Every expectation is a number, read off the shipped page's own canvas in a headless browser, driven through the page's own controls: the real file input, the real buttons, the emulator's real input path.

Two calibration notes, so the numbers above mean what they say. EmulatorJS stretches the SNES's 256×224 picture to 4:3 inside its canvas, so the audit first finds the picture's real box on each screenshot before mapping any coordinate — and that calibration caught its own author once: EmulatorJS's control bar auto-hides over the bottom of the canvas, its fade changed the detected box between screenshots, and the audit briefly reported a failed import that had in fact restored perfectly (proven at the byte level: the banner's 64 tilemap bytes were back in the machine, and the restored state sat 55 bytes away from the disturbed one). The calibration now derives the box's height from the 4:3 aspect instead of the fickle bottom edge, and the finished drive passed 20 / 20 three times in a row. And the fixture caught its author too: its first build assumed the machine's work RAM powers up zeroed, and in this core build it does not — the latch byte started non-zero and the banner logic read garbage until the fixture learned to clear its own variables, the way real hardware would have taught it in 1991. Both of those were the audit's bugs, not the core's, and they are recorded here rather than tidied away.

The pad, measured — this build's big bend

The audit's joypad checks were supposed to be the boring part. They were not. The first pass found the A and B buttons arriving at the cartridge swapped — so the audit stopped trusting labels entirely and mapped the whole pad: a second fixture whose backdrop colour is the pad state, every input index driven in turn, through both the scripted input path and the real keyboard, with the interesting results re-run at long holds to rule out timing. Here is the complete measured map — what EmulatorJS calls each input, which key that is by default, and which bit of the SNES pad registers ($4218/$4219) the cartridge actually sees:

EmulatorJS inputDefault keyWhat the cartridge receives
“B” (index 0)ZA button — $4219 bit 7
“Y” (index 1)AX button — $4219 bit 6
“Select” (index 2)VL button — $4219 bit 5
“Start” (index 3)EnterR button — $4219 bit 4
“Up / Down / Left / Right” (indices 4–7)Arrow keysNo direction bit, ever — two indices land in the pad word's unused low nibble, which no game reads; two land nowhere
“A” (index 8)XB button — $4218 bit 7
“X” (index 9)SY button — $4218 bit 6
“L” (index 10)QNothing arrives — the Select bit it should reach stays silent
“R” (index 11)EStart — $4218 bit 4
Indices 12–23 (L2/R2/L3/R3 and the rest)—Nothing arrives

Read as a pattern, the two bytes of the pad word arrive exchanged — input i drives the button eight places away — and on top of that, Select and all four D-pad directions never reach the cartridge at all through the digital input path, keyboard or scripted. That is the honest headline, and it cuts both ways. What a player can do on the default keyboard: the face diamond works — the keys Z / X / A / S deliver A / B / X / Y exactly as the console page's table now prints them — the shoulders are there (L on V, R on Enter), and Start is there, hiding on E. The buttons that arrive can be remapped in EmulatorJS's controller settings, so a player can put them under sensible keys. What a player cannot do by keyboard on this build is steer: any game that needs the D-pad — which is most of the library — has no directions to steer with. A physical gamepad travels the same input path in EmulatorJS; whether its D-pad fares better was not testable in this audit and is claimed neither way. The bend is upstream's — it lives in how this core build takes its input, not in the house page, which passes the player's input to EmulatorJS untouched — and the console page's Help now prints the measured table rather than the labels, so nobody has to discover it mid-game.

The correction — the pad was never crossed (24 November 2026)

The section above is wrong, and this one is its receipt. What brought it down was the field: Steven loaded one of his own cartridges on the live page — it ran — and reported that the buttons “don't appear to be working at all.” A controls investigation confirmed the crossed map a second time with the same decoder, and a replacement-core hunt was launched on the strength of it. The hunt did the one thing the audit hadn't: it checked the decoder against the hardware itself — the pad layout as the Super Famicom's own documentation and Snes9x's source (S9xDoAutoJoypad) define it. Register $4218 carries A, X, L, R in its high nibble; $4219 carries B, Y, Select, Start, Up, Down, Left, Right. The audit's pad-decoder fixture names those two bytes' bits in swapped order — its own source comment gives it away, labelling the low byte “$4218 (B Y Sl St U D L R)”, which is the high byte's layout written beside the low byte's name. Every reading the fixture ever produced was mirrored: a correctly wired pad photographed as a rotated one, its D-pad bits landing in what the decoder called unused signature bits, its Start read off the bit that actually carries R.

Re-decoded under the true layout, the original sweep is a perfect, unrotated map — and this pass re-measured the shipped defaults directly, with real key presses through the shipped page and the decoder corrected, picture box calibrated on a bright hold so even the two bits a screenshot nearly hides (L and Down each light a single dim channel bit) survive to be counted: 15 / 15 checks. The true map, which is also the console page's printed table now:

So: the core was never cross-wired, on any of its four payloads (the threaded builds were swept with the same fixture, and their readings re-decode to the same perfect map), and no remap ships. This pass began by building one — a rotation, set through EmulatorJS's own settings channel, that would have “corrected” a correctly wired pad into an actually crossed one. It was removed, unshipped and uncommitted, the moment the correction landed. The hunt for a replacement core is called off: there is nothing to replace. (The hunt's one finding that survives re-reading is about the other candidate: the bsnes build in EmulatorJS's unstable line currently doesn't boot at all — a missing-function abort, unrelated to any pad.)

What actually failed the player was the page, twice over. First, the printed table: this console's first key table — and the table in the section above, and the room's shelf lines — taught the crossed map. Start on E, arrows dead. A player following it, on a cartridge that opens at a menu, has no working buttons at all: the game was listening on Enter and the arrows the whole time. Steven's cartridge was a trainer menu, the worst first screen to meet that table with. The table has been corrected everywhere it was printed. Second, the focus trap, which is real: EmulatorJS listens for keys on the game picture itself, so clicking any page furniture — a button, the Help — moves focus out of the picture's subtree and every key silently parks until the player clicks back in. That was measured at the event level in this pass (a keydown's target leaves the game element entirely), and it alone can produce a “totally dead” session on a healthy machine. The cure now ships on the console's face: a note under the screen saying so, a focus outline on the screen box, and the Export and Import buttons handing focus back to the game when they finish — verified by driving them: after either click, a held key delivers with no picture click. Breakage is the only honest audit; this one broke the audit.

The challenge baton, measured

State Code = 1,097,923 characters · the machine inside it = 823,432 bytes A SNES state is the whole machine — 65816, picture and sound chips, cartridge state — so a baton pass here is one very large block of text: copy it, send it, keep it in a note; do not retype it. The same cartridge must be inserted before import; a state is a moment from one specific game, not a game in itself.

The round trip was proven on screen, not just in bytes. The audit fixture's Start latch flips a white banner row: banner on → Export through the page's own button → flip the banner off (the machine has visibly moved on) → Import through the page's own button → banner on again, the exported moment restored where a player can see it. Underneath the picture, the re-serialised machine after import matched the exported state to within 19 bytes of 823,432 — the frame counters, still counting. The wrap is the house page's own work around EmulatorJS's unmodified state calls, carrying this page's SNESSTATE1: prefix.

Why this console is not a Baton Box passenger: the Box serves single, self-contained pages — that is its contract, and it is what lets a game ride it with a manifest alone. The SNES console is a machine room of 49 files (a WASM core cannot be inlined into a page the way the NES console's JavaScript engine could), so there is nothing single-file to register. Its state code is also simply too big for the Box's ~1 MB blob guidance once wrapped — 1,097,923 characters against it. The baton still passes; it just travels by clipboard and message, the way the console page's own baton section says. The NES console and the 6502 Bench ride the Box; this one hands off by hand.

Honest notes

Corrected 24 November 2026 — the pad was never crossed. The limitation this bullet originally announced (a cross-wired pad, a library that can't be steered) was an artifact of the audit's own test cartridge, whose decoder named the joypad's two bytes in swapped order; the full correction and the re-measured map are in The correction above. What genuinely limits play here is smaller and duller: the focus trap (keys park when you click the page's furniture — the cure is printed under the screen), and the emulation caveats below. A cartridge that “doesn't respond” is most likely waiting for a click back into the picture, not for a different core.

The threaded cores sit unused. Two of the four payloads need SharedArrayBuffer, which needs cross-origin-isolation headers this static site doesn't send. They ride along because the rack is vendored whole; the legacy core is what actually runs, and it ran everything the audit asked of it.

One upstream phone-home exists, and it is fenced. EmulatorJS's own code, served from a hostname that is literally localhost or 127.0.0.1, checks its CDN for a frontend update; on any real hostname that code never fires, and if a core file were missing the loader would try the CDN as a failsafe. The rack here is complete, and the audit — served from this very machine — logged zero external requests. The fence is the complete local rack plus a real hostname; both are stated so you can check them.

This console is a rack, not a lone file. The NES console next door was rebuilt so its engine rides inside its page and it works opened as a single saved file. A 6.4 MB WebAssembly rack can't do that trick: the SNES console must be served from its folder — the collection site, or a folder on your own server — over HTTP. Saved alone and opened by itself, it will sit mute, and that is a property of the machine's size, printed here rather than discovered.

No emulation is the hardware. Snes9x is among the most compatible SNES cores ever built, but games that lean on exact timing, mid-scanline tricks, or exotic cartridge chips can still behave differently than they do on a real deck. That trade is upstream's and this page inherits it knowingly.

No ROMs were shipped, downloaded, or touched. The only cartridge in this entire build is the synthetic audit fixture, which lives with the audit notes, not on the page. Steven's library was never copied, listed, or read — the slot reads a file the player picks, on the player's machine, full stop.

The stage guard — a dated note (24 November 2026)

The DOS Console's audit, the same evening, found EmulatorJS's canvas fit latching onto a transient near-zero container height — roughly one boot in two on that page — and never recovering: a folded-away screen. This page runs the same frontend, and its own version of the misfit was quieter but constant: measured across repeated boots, the stage latched at 640×320, a squashed 2:1 box with the 4:3 picture letterboxed inside it, instead of the Super Nintendo's 4:3. The fix is the DOS page's house pattern, page-side only: a CSS guard, #game{aspect-ratio:4/3}, so the stage's height derives from its width and can never collapse, plus a resize nudge just after a game starts so a fit that sampled mid-layout gets a second chance in the guarded box. Measured after: 640×480 on six of six boots, canvas attribute and box in agreement, the picture filling the frame. Credit for the find belongs to the DOS audit; this page just inherits its cure.

The public shelf — added 24 November 2026

This console gained the family's second door the same evening as its siblings: a public shelf block directly under the baton, pointing at the Internet Archive. Three starter titles stand on it — Star Fox (star-fox-u-v-1.0_202503), Super Mario World 2: Yoshi's Island (super-mario-world-2-yoshis-island-usa-rev-a), and the public-domain SNES Slideshow Demo (snes-slideshow-demo-gdqmagichat) — and a paste-a-link field resolves any Archive item page to its cartridge files through the Archive's metadata API. The house rule survives intact: the Archive hosts and serves the cartridges; this page hosts none, downloads none, and keeps none.

Why the shelf is a door and not a slot — the CORS evidence. The Archive's metadata API answers any page: it sends Access-Control-Allow-Origin: *, so resolving an item link works from this page today. Its file servers send no Access-Control-Allow-Origin header at all — traced end-to-end, on the /download/ redirect and on the file response alike — and a browser may not hand a page bytes it was never given permission for. So the cartridge bytes cannot be fetched into this console, on any of the consoles, until the Archive changes that one header. Relaying the bytes through a server of ours would defeat the wall and the rule at once — we would be re-serving other people's cartridges — and was named and declined in the feasibility pass.

The interim form, and the upgrade path. As shipped, the shelf's buttons and every resolved cartridge open the Archive's own player page for the item, in a new tab — the same file, read in their house. The block is built so that exactly one function is the hand-off: the day the file servers send the header, that function alone changes — fetch the bytes, hand them to EmulatorJS as the cartridge (EJS_gameUrl accepts a File), the same local-file path the slot above uses — and the parsing, the file list, and the failure sentences (not a cartridge; a bare .bin whose machine can't be told from its name; a cartridge for a different machine; an item with no cartridge in it) stay exactly as they are. This console reads .smc / .sfc natively and a .zip holding one — the shelf presents zips as readable here, unlike its NES sibling, whose engine takes bare cartridges only. The console itself is untouched: the audit's zero-network story still describes the machine; the shelf speaks to the Archive only when a visitor uses it, and the page's Help says so.
