The 2600 Console — the lesson

Steven Powell's commission was one line: “Build it — reuse Javatari, my ROMs.” The design follows from the second half. Steven's cartridge library is his — it lives on his own shelves and drives, and none of it can or should ship with a web page. So this room ships the other half of the arrangement: the console. A real Atari 2600 emulator, taken unmodified from its author, set into a page with an empty cartridge slot — and the audit below, which drove the machine with a cartridge written for the occasion, because a console you haven't watched run is a claim, not a receipt.

The machine being emulated

The Atari 2600 is the paradox of classic emulation: the smallest machine of its era and one of the hardest to imitate, because it has almost no hardware to imitate. There is no framebuffer. The TIA chip draws the television picture one scanline at a time, in real time, and the CPU — a 6507, the 6502's little brother in a cheaper package — must race the beam, rewriting the picture registers mid-line to compose each row before the electron gun arrives. It has 128 bytes of RAM. Every 2600 game is choreography timed against a moving beam, and an emulator earns its name only by keeping that timing honest, cycle by cycle. That is what Javatari does: a real TIA emulation, not a slideshow of screenshots — which is why this room reuses it instead of pretending a weekend reimplementation would be its equal.

The audit — a cartridge written to be caught lying

No commercial game was used, and none was needed. The audit cartridge, TEST2600, is a synthetic 4K ROM (SHA-256 cc2aea05…ed32bed0e7f90) hand-assembled for this page: a standard 262-line kernel that paints a white playfield band (PF1 = $FF, COLUPF = $0E, reflected) over a background whose colour reports what the program can see. Hold the joystick Up and the background turns orange-red for exactly as long as you hold it; tap Down and a mode counter in RAM steps the background blue → green → violet. If the emulator runs the code, the colours must follow the inputs — there is no way to fake it with a static picture. The ROM was loaded through the console's own drag-and-drop path in a headless browser, the rendered canvas was sampled pixel by pixel, and the save-state machinery was driven through its own menus and keys. 17 of 17 checks passed, with zero page errors:

Two honest boundaries on what this proves. Pixel sampling proves the machine produced the frames the code demanded, inputs included — it does not by itself prove cycle-exact TIA timing on the pathological tricks a handful of cartridges use, and no such claim is made. And the cartridge was loaded by a robot hand performing the same drop a visitor's hand performs; the path is the page's own, but Steven's first real cartridge, dropped from his own library, is the receipt that closes this room — the same rule as every other bench in Nerd Heaven.

Offline, verified — and the two doors that exist

The emulator file was read before it was trusted. Its only network-capable code paths are (a) loading a ROM or state file from a URL you supply, and (b) NetPlay, which connects to Javatari's session service if you open its dialog and host or join. Neither fires on its own; this page supplies no URLs and opens no dialogs. The audit's request log is the receipt: across the whole driven session, the console asked the outside world for nothing. Your cartridges are read by your browser, on your machine — including from a mapped network drive, which to a file picker is simply a folder — and they are never uploaded anywhere.

The challenge baton — honestly a file, not a code

Save states work two ways. Slots live in this browser (Ctrl+number saves, Alt+number loads) — quick, and gone if the browser's site data is cleared. Files are the durable form: Save State → File… downloads a small .jst, and Load State → File… (or dropping the file on the screen) restores the frozen machine anywhere. That file is the challenge baton this room was built around: freeze a brutal moment, hand the file on, and the next player's turn is to survive it.

The honest part: a .jst is a file, not a copy-and-paste code — so the 2600 Console is not registered as a Baton Box passenger. The Baton Box's contract is a blob you can paste; Javatari offers no such blob, and this room does not pretend otherwise. The baton here travels hand to hand — email, USB stick, or the same shared folder the cartridges already live on. If the Box ever learns to carry files, this console is first in that queue.

Bends — what's not perfect, said out loud

  • Accuracy has a known ceiling, and the author says so. Peccin himself notes Javatari is a little less accurate than desktop Stella for some known, extremely rare TIA tricks — the class of thing a tiny number of cartridges rely on. For the ordinary run of the library it is a faithful machine; for that rare trick, Stella is the reference, and this page won't pretend the gap isn't documented.
  • NetPlay exists. It is upstream's feature, off unless a visitor opens it and hosts or joins, at which point it talks to Javatari's session infrastructure. Nothing on this page starts it; the Help notes say the same.
  • Slots are browser-local. Save slots live in this browser's storage on this machine. The .jst file is the form that travels and lasts.
  • Names are trademarks. Atari, VCS and the Atari logo belong to their owners. They are used here descriptively, as a tribute — upstream prints the same note — and no cartridge, commercial or otherwise, is included with or downloadable from this room.

The public shelf — added 24 November 2026

The console gained a second door the same evening: a public shelf block directly under the cabinet, pointing at the Internet Archive. Three starter titles stand on it — Moon Patrol from the Console Living Room (Moon_Patrol_1983_CCE_C-1006) and two homebrew cartridges, Oystron (Oystron_1998_Xype_Piero_Cavina) and Halo 2600 (Halo_Atari_2600), each a bare .bin — and a paste-a-link field resolves any Archive item page to its cartridge files through the Archive's metadata API. Steven's direction, and the house rule survives intact: the Archive hosts and serves the cartridges; this page hosts none, downloads none, and keeps none.

Why the shelf is a door and not a slot — the CORS evidence. The Archive's metadata API answers any page: it sends Access-Control-Allow-Origin: *, so resolving an item link works from this page today. Its file servers send no Access-Control-Allow-Origin header at all — traced end-to-end, on the /download/ redirect and on the file response alike — and a browser may not hand a page bytes it was never given permission for. So the cartridge bytes cannot be fetched into this console, on any of the consoles, until the Archive changes that one header. Javatari even ships its own URL loader — the readFromURL path named in the offline section above — and it is walled by the same missing header. Relaying the bytes through a server of ours would defeat the wall and the rule at once — we would be re-serving other people's cartridges — and was named and declined in the feasibility pass.

The interim form, and the upgrade path. As shipped, the shelf's buttons and every resolved cartridge open the Archive's own player page for the item, in a new tab — the same file, read in their house. The block is built so that exactly one function is the hand-off: the day the file servers send the header, that function alone changes — hand the resolved file's URL to Javatari's own URL loader, upstream unmodified — and the parsing, the file list, and the failure sentences (not a cartridge; a cartridge for a different machine; an item with no cartridge in it) stay exactly as they are. The offline section above still describes the console itself: the shelf speaks to the Archive only when a visitor uses it, and the page's Help now says so.
