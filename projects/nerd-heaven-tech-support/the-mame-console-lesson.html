The MAME Console — the lesson

The arcade machine room of the console shelf — every golden-age board emulated in one page, and, like every machine here, it ships with no games at all. What it plays is a romset: the zip from your own archive, named by its shortname, read on your machine and kept on your machine. Under the hood is MAME 2003-Plus, a libretro core built on the MAME 0.78 codebase, running inside the EmulatorJS frontend — both embedded unmodified, both licenses carried with the page. This page is the receipt: where they came from, the license reasoning in plain words, what was verified by driving the shipped page with mamedev's own free romsets, and the honest limits — including the one this audit is proudest of: the first key map printed for this cabinet was wrong, the audit caught it before Steven ever saw the page, and the correction is documented below rather than quietly swept away.

Where this one came from

The consoles came in a ladder across one long day: the 6502 Bench, the 2600, the NES, the SNES, the DOS machine, the Apple IIe. MAME was named early and deliberately held — Steven, when the ladder was still being climbed: “once I see what we have already done run a couple of roms that encore may be called before the night is up.” A plan was written and banked in the afternoon (route, romset problem, licensing, audit fixtures) so the build wouldn't need re-researching. That evening he ran his own cartridges through the finished consoles — Chip 'n Dale on the NES, Asteroids and Video Pinball on the 2600 — and Leigh played Oregon Trail on the IIe. Then, at 21:49: “oh definatley do mame and the rest of the tests.” The encore was called by the man who set its trigger, after the trigger was met. This build follows the banked plan, with two of its assumptions corrected by measurement along the way — both corrections are in this lesson, in the open.

What MAME 2003-Plus and EmulatorJS are

MAME — the Multiple Arcade Machine Emulator — is the decades-long project to document and emulate arcade hardware board by board. A MAME core does not play “ROMs” in the loose sense; it plays the exact romset built for its version: a zip named by shortname (pacman.zip) holding specific files of specific sizes. Feed a core the wrong vintage of set and the board refuses it or runs it wrong. That single fact shapes everything about this console.

MAME 2003-Plus is the libretro core built on the MAME 0.78 codebase (December 2003), actively backported with later fixes and added games; it accepts 0.78 romsets for the overwhelming majority of its catalogue, and it was designed to run full-speed on a Raspberry Pi — the whole classics era is effortless in WebAssembly. The frontend is EmulatorJS 4.2.3, the same stable line and the same vendored-rack pattern as the SNES and DOS consoles beside it. One scoping fact, established from the frontend's own source rather than memory: EmulatorJS's arcade shelf offers exactly three cores — mame2003_plus, mame2003, and fbneo. There is no current-MAME libretro core in EmulatorJS, so a browser MAME through this frontend is vintage-pinned by design. That is a feature when the archive matches, and the romset section below is about finding out whether it does.

The license question, in plain words — with a correction

The build plan for this console recorded the core's license as “GPL-2.0-or-later,” following current MAME, which was relicensed in 2016 (the project as a whole GPL-2.0-or-later, most files BSD-3-Clause). That was wrong for this core, and the build caught it: the artefact that ships is not current MAME. The MAME 2003-Plus core's own repository carries its license in plain sight, and it is the classic MAME non-commercial license — the MAME 0.78 Usage and Distribution License — because a 0.78-derived codebase predates the relicensing and its backports ride under the old terms unless a file says otherwise. That text is what is vendored in the rack, verbatim from the core's repository (LICENSE-mame2003-plus.md), because the npm core package ships no license file of its own. Like Snes9x's terms on the neighbouring console, it fits a personal, non-commercial collection on its face: use it, don't sell it, keep the notice. The EmulatorJS frontend is GPL-3.0; its license is vendored beside it.

The trademark flag, as the plan directed: MAME® is a registered trademark of Gregory Ember, and the MAME team's rules ask permission for use of the name in products. This page's use is descriptive — a fan-made loader page that names the emulator it embeds, with the credit and this acknowledgment on its face and the trademark line in its footer — the same posture as the other consoles' names on this shelf. It is recorded here, in the open, as Steven's to revisit; if he ever wants the cabinet renamed around it (“The Arcade Loader, powered by MAME”), that is a one-line change and his call.

And the standing rule of the whole shelf holds: the machine ships, the games don't — no romsets are in this build. The only ROMs the audit touched are mamedev's own free ones, under their terms, below.

The threading verdict — this one runs on the plain site

The DOS Console beside this one is exhibit-only on the website: its core ships threaded builds only, threaded builds need cross-origin isolation, and a static host can't send the headers. The first question this build had to answer was whether the arcade core has the same cage. It does not, and the verdict is measured, not inferred:

  • The core package ships a non-threaded payload alongside the threaded ones, and its build report declares no thread requirement.
  • The frontend's own requires-threads list, read in its shipped source, is exactly ["ppsspp", "dosbox_pure"] — this core is not on it.
  • The console page therefore never sets EJS_threads, and the audit booted both fixtures on a plain local server with window.crossOriginIsolated === false asserted in the page — no COOP/COEP headers anywhere — and played them. This console runs on GitHub Pages as Pages serves today.

This is a 49-file rack, like the SNES; its state codes travel by clipboard and message, as the SNES's do.

The audit — mamedev's free romsets, driven through the shipped page

A MAME core can't boot a hand-built synthetic ROM the way the other consoles could — a “game” is a driver plus a matched set. The fixtures are therefore mamedev's own free ROMs: arcade sets released by their rights holders for free non-commercial use, distribution from mamedev.org only. Two were downloaded from mamedev.org/roms/ at audit time, into the audit workspace only: Robby Roto (Bally/Midway, 1981; robby.zip, 27,915 bytes, sha256 d3f7ae3a…0a8d8) and Gridlee (Videa, 1982; gridlee.zip, 25,516 bytes, sha256 df977ceb…056e). They are not in this repository, were never committed, and are never mirrored — that is a term of the grant, and the shipped page contains no games, as always. Both fixtures are documented running on MAME 2003-Plus specifically, and both were driven headlessly through the shipped page's own slots, on the plain non-isolated server described above.

What passed, in order:

  • Boot and attract, both fixtures. Robby Roto reached its attract loop — the blue maze demo, sprites, the © MCMLXXXI BALLY/MIDWAY line — and Gridlee reached its own live attract (a 32-colour sampled frame). The marquee lit with the right title and the raw shortname underneath, as designed.
  • The cabinet geometry. The canvas measured exactly 840×630 inside the stage box, before and after the resize nudge — the 4/3 aspect guard the SNES correction bought is structural here from birth.
  • The full player sequence, by keyboard only, on the final shipped page: click the screen → work the stick left-then-right → hold V → hold Enter → the maze persisted across frames (blue fraction 0.802) and Robby carved through it under joystick holds, the field giving way to his trail (0.802 → 0.42 across four seconds of play), caged enemies and the magic item on screen. Coin, start, and joystick are proven at the cabinet, not inferred from a config file.
  • The state round trip. Robby Roto's whole machine exported as a MAMESTATE1: code of 35,147 characters (26,352 bytes); after the game was played on, Import restored it and the page said so. Small board, light baton — a sixth of the DOS code, a thirtieth of the SNES's.
  • The request log. A cold session made 23 requests. Twenty-two were same-origin — the page and its rack. The one exception is named under Honest notes.

What the audit caught — three findings, all fixed or confessed before shipping:

  • The warning screen eats first. A freshly booted board shows the core's copyright warning, and while it stands, coin and start presses are consumed by it — the audit's early drives pressed correct keys at a warning screen and measured silence. Working the stick (arrows, left then right) dismisses it; only then does the board hear the liturgy. The page now teaches the dismissal first, in the strip under the screen.
  • The first liturgy was wrong — the SNES lesson, learned twice. The page was first drafted with desktop MAME's canon printed on the cabinet: 5 coin, 1 start. In this stack a pad layer sits between keyboard and board, and those keys do not mean that here — worse, 1 is the frontend's quick-save. The true map was read off the running emulator's own control table and then proven at the cabinet: coin (SELECT) = V, start = Enter, buttons Z X A S, shoulders Q / E, joystick on the arrows. The cabinet, the Help, and the status lines were all corrected to the measured map before the page shipped, and the Help explains the 5-and-1 story and how a player can remap the canon back in the toolbar if they want it. A printed key table is a promise; this one is kept.
  • The parent/BIOS slots, as first wired, hung the boot in silence. Handing the frontend a parent or BIOS File object — the way the game slot legitimately takes its file — throws inside the frontend's cache check (it calls .split("/") on the value), inside a promise that then never settles: no error, no canvas, a dead cabinet. Measured, traced to the line, and fixed page-side (upstream untouched): the page now hands those two hooks a blob URL — the file's own local address. Re-driven with both optional slots filled, the machine starts clean. The honest limit: the smoke test used stand-in files, because mamedev's free shelf holds no clone or BIOS-dependent set; the mechanism is the frontend's own designed path, but a true clone-plus-parent boot waits on a real split set — Steven's archive is where that receipt will come from, and this lesson says so in advance rather than after.

The romset problem — and the diagnostic that answers it

Everything above proves the machine. It does not prove the machine matches Steven's archive, because that archive's vintage is still unknown — the plan named this the make-or-break question, and it stays open until it's measured. Beside this lesson sits mame-romset-diagnostic.py: a small read-only script (Python, standard library only) that he runs against the archive himself. It reports the top-level folder names, the set census, the telltale neighbours (a samples/ folder, CHDs, .dat files), and the directory listings — file names and sizes only, nothing extracted — of the three fingerprint sets pacman.zip, dkong.zip, and neogeo.zip. Folder names alone often confess the vintage; a full 0.78 set is roughly 4,700 zips where a modern one is several times that; the fingerprints read like tree rings against the published per-version data. The script was self-tested against a synthetic archive before shipping. Its verdicts are printed in its own header: 0.78 → this core; FBNeo → a different, rolling vintage this core will largely refuse; a current-MAME archive → the honest answer is that this is the wrong machine for most of it, said plainly rather than forced. Steven's first run — the diagnostic, then one of his own zips in the slot — is this console's field receipt, declared here in advance, the way the plan wrote it.

Honest notes

The one phone-home attempt. The frontend, unmodified, tries once per session to fetch a version file from cdn.emulatorjs.org. It is upstream's own update check — the DOS Console's audit met the same call — it carries no data about the player or the romset, it is not needed for play, and offline it simply fails (the sandbox's log shows it dying against the proxy while the games played on). It is named here because “zero external requests” would otherwise be a claim this page couldn't keep.

Two page errors, both upstream, neither touches play: that version check's failed fetch, and the frontend's wake-lock request, which headless browsers deny (the SNES audit met the same denial).

States are per-driver. Robby Roto's state exported and restored cleanly. Gridlee's driver returned a state of zero bytes — the page's Export reported “Size is zero” instead of handing over an empty code. MAME 2003-Plus state support genuinely varies by board; where a board has none, this console says so. And all codes are core-build-fragile: they belong to this exact core build, on this console.

Out of scope, on the page's face: CHD games (the hard-disk era — Killer Instinct, Area 51, Blitz) and the 90s 3D boards are beyond a 2003 core; a handful of games keep some sounds in a separate samples set and play those sounds missing without one; vertical games play letterboxed. None of these is a bug in the page, and none is hidden.

The audit's ground. Drives ran headlessly against a plain local server — Steven's environment lesson (he opens lone files and real sites, not served folders) is answered by the file:// guard being driven too, and by the live-site verification recorded in the wiring receipts. His own archive remains, as ever, the final receipt.

On the live site — 24 November 2026. The wiring commit (ad50671) built on GitHub Pages, and the served console page is byte-identical to the audited file (sha256 e92755f7… both ways), with every rack asset serving 200 at its exact size. The audit's sandbox could not drive the live page headlessly — its browser egress dies at the proxy tunnel (ERR_TUNNEL_CONNECTION_FAILED), the known failure — so the live receipt rests on that byte-identity plus the full local drive above, and, as declared, on Steven's first run with a romset of his own. That run is still his to give.
