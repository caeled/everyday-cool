Sorting Trees Race — the lesson

Sorting looks trivial until you count. Every algorithm that puts a list in order pays for it in two currencies — comparisons (asking "which of these is bigger?") and writes (moving elements around) — and the exchange rate between them is the whole subject. Insertion sort pays almost nothing on a nearly-sorted list and a fortune on a reversed one; quicksort is fast until a bad pivot turns it quadratic; radix sort refuses to compare anything at all. This exhibit — AlgoArena — races seven real implementations side by side on identical inputs, counts every comparison and write as it goes, and then does the same honesty exercise for a red-black tree, the self-balancing search tree that keeps its lookups logarithmic by enforcing five invariants after every insert and delete. This page is the other half: the counting the race runs on, and the audit that drove the shipped code and checked its counters against theory — to the digit.

Verdict: The wave's most numerically honest exhibit — all seven sorts' comparison and swap counters match theory to the digit on driven inputs, the quicksort worst case is genuinely disarmed (median-of-three pivot + 3-way partition), and the red-black tree survived a 3,000-operation fuzz against an independent invariant validator — with bends only in the framing: the race's shared "ops" currency mixes unlike units, merge-family write counts are undercounted exactly 2×, and its "Timsort" is a simplified teaching variant, not CPython's.

The concept

Counting is the science

Big-O notation is a sorting algorithm's reputation; the counters are its receipts. Theory makes exact predictions at the extremes — insertion sort on an already-sorted list of 64 must compare exactly 63 times, no more, no less — so an implementation can be checked the way a scale is checked: with known weights. The race runs seven sorts (insertion, merge, quicksort, heapsort, Shellsort, radix, and a Timsort variant) over five input distributions — random, nearly-sorted, reversed, organ-pipe, and few-unique — because an algorithm's cost is a property of the algorithm and the input together.

The quicksort trap, and how you disarm it

Quicksort picks a pivot, partitions around it, and recurses. Pick the pivot naively — say, always the first element — and already-sorted input becomes the worst case: every partition peels off one element, and the cost goes quadratic, about n²/2 comparisons. The standard defences are a median-of-three pivot (sample first, middle, last; take the median) and a 3-way Dutch-national-flag partition that sweeps all duplicates of the pivot out of the recursion in one pass. Whether the exhibit's quicksort actually carries those defences — or just says it does — is measurable, and the audit measured it.

Red-black trees: balance by invariant

A plain binary search tree fed ascending keys degenerates into a linked list: insert 1..99 in order and the "tree" is 99 tall. A red-black tree colours every node red or black and enforces five invariants — root black, no red node with a red child, equal black-height on every root-to-leaf path, and the rest — repairing violations with rotations and recolouring after each operation. The payoff is a hard height bound: no red-black tree is ever taller than 2·log₂(n+1). The exhibit verifies its five invariants live, and displays the naive tree's height next to its own for the same input.

The concept/math

The exact counts theory predicts

insertion, sorted: n − 1 comparisons  ·  insertion, reversed: n(n−1)/2  ·  mergesort writes: n·lg n At n = 64 those are 63, 2,016, and 384 — exact integers, not estimates. Mergesort's comparison worst case is bounded by n⌈lg n⌉ − 2^⌈lg n⌉ + 1 = 321 at n = 64, and its best case is (n/2)·lg n = 192. Heapsort stays under 2n·log₂n. Any honest counter has to land on or under these numbers; the audit table below shows where each one landed.

The non-comparison sort, and the tree bound

radix: 0 comparisons, ops = 2n × digit passes  ·  red-black height ≤ 2·log₂(n + 1) LSD radix sort never compares two elements — it buckets by digit — so its comparison counter must read exactly 0 and its op count must be identical on every input distribution. At n = 99 the red-black bound is 2·log₂(100) = 13.3: a correct tree answering to it can be 11 tall, but never 14.

The audit — claims checked against the code, with receipts

The audit extracted the exhibit's own shipped scripts and ran them headlessly in Node under a DOM stub: the page's own generators, SortRunner, race driver (advanceRaceOp), and RedBlackTree were executed and driven, and the counts below were measured from that code and checked against published theory and an independent red-black validator written separately in the harness. The exhibit file was not edited.

Receipt 1: all seven sorts are correct, on every distribution

Each shipped generator was run to completion through the page's own SortRunner at n = 64 on all five offered distributions. In all 35 runs the output was sorted, was a permutation of the input, and was confirmed by the page's own verification sweep (verified = true). No failures.

Simplifications and divergences, named

The race's shared "ops" currency mixes unlike units: the race steps each lane exactly one generator yield per tick, and that part is implemented honestly — on identical input, every lane's race finishOps exactly equals its solo-run ops (verified for all four Classic Clash lanes on random and reversed inputs: radix 336 = 336, insertion 1,665 = 1,665). But a yield is a different amount of work per algorithm: a comparison = 1 op; a swap = 1 op that performs 2 writes (quicksort's 632 ops = 336 compares + 296 swaps, while its writes total 592); a radix bucket placement = 1 op; a mergesort auxiliary copy = 0 ops. So the ops leaderboard ranks algorithms by animation steps, not by equal work. "Equal Ops/Tick" is literally true and still not an apples-to-apples speed measure. The page does not claim wall-clock timing as algorithm speed; the bend is confined to the shared ops counter.

Merge-family "Array Writes" are undercounted exactly 2×: mergesort's counted writes are 384 — one yield per element written back per level — but each merge first copies the working range into an auxiliary buffer without yielding, so true element assignments are 768. The exhibit's Timsort variant has the same merge structure and the same undercount. The counter is self-consistent as a count of the write events the animation shows, but as an "Array Writes" statistic it halves the merge family's real write traffic — and it is compared in the UI against algorithms (insertion, quicksort) whose counters do capture every assignment.

"Timsort" is a simplified teaching variant, not CPython's: what ships genuinely detects natural runs, extends short runs with insertion sort, and merges runs — and the adaptivity is measurable, not marketing: sorted input costs exactly 63 comparisons (one run), reversed costs 63 comparisons plus reversal swaps, and nearly-sorted (165 cmp) beats random (448 cmp) by 2.7×. But real Timsort (Python/Java) uses minRun 32–64 (the page: 8/16), a run stack with merge invariants, and galloping; the page merges pairwise bottom-up with none of those. The mechanism taught is real; the name promises the production algorithm.

Smaller print: the Shellsort description omits gaps the code uses. The code's Ciura sequence is [701, 301, 132, 57, 23, 10, 4, 1]; the UI description says "(57, 23, 10, 4, 1)". At n = 64 the used sequence is exactly [57, 23, 10, 4, 1], so the description is accurate there — but at n = 150 the code uses [132, 57, 23, 10, 4, 1], the 132 gap the description never mentions. Race finishRank is assigned when a sort's generator completes, before its verification sweep runs — cosmetic; the sweep has never failed in testing. And a note that is not a bend: radix op/write counts are identical (384) on every distribution, which is correct behaviour for an LSD radix, and the page's distribution-independence framing is accurate.
