Pipeline — the lesson

A processor that finishes one instruction before starting the next would spend most of its life waiting. A pipelined processor overlaps them instead: while one instruction executes, the next is decoded and the one after that is fetched — five stages (fetch, decode, execute, memory, write-back) working on five different instructions at once, like an assembly line. The catch is that instructions depend on each other, guess wrong about branches, and wait on memory, and every one of those catches costs cycles you can count. This simulator runs a 5-stage RISC CPU with an assembler, data forwarding, a branch predictor, and a small L1 cache — and this page is the other half of it: the ideas, the arithmetic, and the audit that checked every preset's printed numbers against pipeline schedules derived by hand.

Verdict: PASS-grade — every preset's cycle counts reproduce hand-derived pipeline schedules exactly (12 cycles with forwarding, 24 without on the RAW preset; the branch predictor's 2 mispredicts are exactly what a real 2-bit counter + BTB predicts), and the bends are labelling, not physics: the "Branch Flushes" counter counts slots rather than events without saying so, cache-OFF still counts misses, and CPI includes pipeline fill and drain.

The concept

Five stages, overlapped

Each instruction passes through IF (fetch), ID (decode and read registers), EX (execute), MEM (memory access), and WB (write the result back). In a steady pipeline one instruction retires per cycle — but the first instruction still takes five cycles to get through, and that fill cost is in every measurement this simulator makes, including the short ones. The exhibit's Gantt view traces each instruction through the stages, and the audit checked that its write-back cells match the retired count and that no instruction's stage order ever runs backwards.

Hazards: when the line has to wait

A data hazard happens when an instruction needs a result that an earlier instruction hasn't written back yet — a read-after-write (RAW) dependency. The hardware has two answers. Forwarding (also called bypassing) routes the result straight from the EX or MEM stage to the instruction that needs it, without waiting for write-back: EX→EX and MEM→EX paths, both wired in here. The one case forwarding can't fully cover is the load-use hazard: a load's data only exists at the end of MEM, one stage too late for the very next instruction, so even with forwarding on it costs exactly one bubble. Turn forwarding off and the same programs stall the honest, slow way — the RAW preset takes exactly twice as long, 24 cycles against 12.

Branches: guessing, and paying for a wrong guess

A branch isn't resolved until EX, but the pipeline has to fetch something in the meantime. A branch predictor guesses: here, a 2-bit saturating counter (which needs to be wrong twice in a row before it changes its mind) plus a branch target buffer (BTB) that remembers where each branch went last time. Guess right and the branch costs nothing; guess wrong and the speculatively fetched instructions are flushed — wasted slots. With prediction off, the exhibit always predicts not-taken. With it on, a loop branch still mispredicts exactly twice: once cold, before the BTB knows it, and once at loop exit, when it finally stops being taken. That is not a bug in the exhibit — it is what the real hardware does, and the audit's hand count agrees.

The cache: small, fast, and geometric

Main memory is slow, so an L1 cache keeps recently used words close. This one has 4 sets of 2-word lines (8 bytes a line): consecutive words share a line, so reading a neighbour is a hit (spatial locality), but two addresses that land in the same set evict each other — the cache preset's thrash pattern, addresses 0 and 32 fighting over set 0, is exactly what its counters record. A miss costs the penalty set by the slider, 1–5 cycles.

The concept/math

The ideal pipeline, and what CPI really counts

N instructions, hazard-free: N + 4 cycles  ·  CPI = total cycles / instructions retired  ·  IPC = 1 / CPI The +4 is the fill: the first instruction needs all five stages before anything retires. Because CPI here divides total cycles by retired instructions, fill and drain are included — a hazard-free 3-instruction program (3 independent ADDI + HALT) retires at cycles 5/6/7 and shows CPI 7/3 = 2.3333. That is the standard definition, but it makes short programs look artificially bad. Live check from the audit: the branch preset halts at cycle 35 with 21 retired, and the display reads CPI 1.67 / IPC 0.60 — the definition, applied honestly.

The hazard arithmetic

RAW chain, forwarding ON: 7 cycles, 0 stalls  ·  forwarding OFF: 11 cycles, 4 RAW stalls Forwarding removes every stall in a pure ALU dependency chain. The load-use case is the exception the formula can't remove: LW followed immediately by a dependent instruction costs 1 bubble even with forwarding, because the loaded value arrives at the end of MEM. On the load-use preset program (miss penalty 2) the audit measured 1 load-use stall, 1 miss, 2 miss-stall cycles, 3 stall cycles total, 10 cycles overall.

Cache geometry

set = (wordAddr >> 1) & 3  ·  tag = wordAddr >> 3  ·  4 sets × 2 words = 8-byte lines The code's set/tag split matches the "4 sets × 2 words (8B line)" label on the page exactly. Addresses 0 and 32 both map to set 0 with different tags, which is why the cache preset thrashes there while neighbouring words hit.

The audit — claims checked against hand-derived schedules, with receipts

The audit extracted the exhibit's simulation core verbatim (the fenced // === SIM CORE START/END === section), ran it in Node against pipeline schedules derived by hand, independently of the code, and also drove the shipped page through its real DOM — preset buttons, toggles, sliders, transport buttons, and the assembler — in jsdom. 33 core checks ran; every preset value below matched. The only disagreements in the whole run were 3 cycle totals on the load-use program, and investigation showed those were the auditor's own hand-trace error, not the simulator's (see the bends, below).

Bends and simplifications, named

"Branch Flushes" counts slots, not events: each misprediction adds the number of in-flight slots flushed (2 in this pipeline — the ID occupant plus the speculative fetch slot, and a fetched HALT marker can be one of them), with a floor of 1. So the same branch run reads "Branch Flushes 10" in the telemetry and "Mispredicts 5" in the Hardware tab. Both numbers are defensible; the page never says they measure different things.

Cache OFF still counts "misses": with the cache disabled, every access increments the L1 Misses counter and the hit-rate readout shows 0% rather than "bypassed". The timing behaviour matches the label ("OFF forces RAM stalls" — the full miss penalty is charged), but the counters present a disabled cache as a 0%-hit cache.

CPI includes fill/drain: CPI = total cycles / retired, so a hazard-free 3-instruction program shows CPI 2.33. Standard for this definition; short programs look artificially bad, and the page doesn't warn you.

Predictor warm-up is BTB-gated: a branch is only predicted taken once its BTB entry exists and the 2-bit state is at least weakly-taken, so the first taken branch always mispredicts, and jumps (J) are predicted not-taken until first executed (measured J-loop, predictor on: 2 mispredicts across 5 control transfers). True to the implemented design, but the "Predicts taken loops" label glosses over the cold-start cost.

Unlabelled simplifications: MUL completes in one EX cycle (no multi-cycle multiply); RAM is 64 words with silent address wrap (wordAddr & 63 — byte address 256 aliases word 0) while the UI displays only words 0–17.

One for the auditor: on the cycle a cache fill completes, the instruction held in ID decodes in that same cycle — correct latch semantics (simultaneous MEM→WB and ID→EX movement), and the same convention reproduces the branch-flush totals exactly. It is why the load-use program totals 10 cycles at penalty 2, not the 11 a hand-tracer (this one included) first writes down.

FALSE findings: none. Every quantitative claim on the page that was tested reproduced exactly.
