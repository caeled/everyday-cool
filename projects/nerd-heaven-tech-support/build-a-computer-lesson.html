Transistor Up — the lesson

The bench builds a computer in front of you, one layer at a time, and every layer is made only of the layer below it. A transistor used as a switch becomes a gate. Gates become an adder and, cross-coupled, a memory. An adder plus memory plus a clock-stepped control becomes a CPU. And the GPU is what happens when you stop asking one worker to do everything in sequence and instead give the same small job to many workers at once. This page is the other half of the bench — the stack, the worked answers, and every simplification named.

The stack, bottom to top

  1. Fab / transistor. A transistor is a switch with no moving parts: a signal on the base decides whether current may flow between collector and emitter. The bench models exactly that decision and nothing more — see the bends.
  2. Gate. Put a transistor in a pull-down path and the path conducts or not. One transistor gives NOT. Two in series give NAND, because the output falls only when both conduct — series conduction is the AND of the conduction states, evaluated by the core, never looked up in a table. NAND matters out of all proportion to its size: it is functionally complete, meaning every other logic gate can be built from NANDs alone, and on the bench every other gate is.
  3. Adder. XOR, AND and OR composed from NANDs give a 1-bit full adder; four full adders chained carry-to-carry give a 4-bit ripple adder. This is arithmetic built from switches, with the carry visibly rippling from bit to bit.
  4. Memory. Feed two NAND gates into each other — each output is the other's input — and the circuit has two stable states and no reason to leave the one it is in. That is an SR latch: one bit of memory made of pure feedback. Four latches side by side are a 4-bit register.
  5. CPU. Give the machine a memory of 16 nibbles, an accumulator register (those same latches), a program counter, and a small instruction set, and step it: fetch the opcode nibble and operand nibble at the PC, do the thing, advance. The bench CPU's ADD instruction literally calls the stage-(c) ripple adder; its SUB is the same adder fed the inverted operand with carry-in 1, which is two's-complement subtraction.
  6. GPU. A CPU is one fast worker following instructions in order. A graphics processor is the opposite organisation: thousands of small workers all doing the same operation to different data at the same time. The bench's GPU wing models that organisation on a 16×16 pixel grid and counts the modelled steps both ways.

The formulas

NOT A = A conducts ? 0 : 1  ·  NAND(A,B) = series(A,B) conducts ? 0 : 1 The transistor network is the definition. The pull-up holds the output at 1 unless the pull-down network conducts and drags it to 0. Series conduction = AND of conduction states; parallel conduction = OR.
AND = NOT(NAND)  ·  OR = NAND(NOT A, NOT B)  ·  XOR = NAND(NAND(A,D), NAND(B,D)), D = NAND(A,B) Every gate in stage (b) is a composition of the transistor-network NAND — De Morgan's law for OR, and the classic four-NAND construction for XOR.
sum = A ⊕ B ⊕ Cin  ·  Cout = (A·B) + ((A⊕B)·Cin) The full adder. Chain four of them, each Cout feeding the next Cin, and you have the 4-bit ripple adder. The bench adder takes a carry-in: it is 0 in the panel, and the proofs exercise carry-in 1 as well.
arithmetic is mod 16:   15 + 1 = 0, carry out = 1 A 4-bit register holds 0–15 and nothing else. Overflow does not error — it wraps. The demo program (1+2+3+4+5 = 15) was chosen to land exactly on the largest representable value, one step before the wrap, so the boundary is visible rather than theoretical.
serial steps = N  ·  parallel steps = ceil(N / lanes) For the GPU wing: N = 256 pixels, lanes = 16, so 256 modelled steps serially against ceil(256/16) = 16 modelled steps in parallel — a 16× step-count reduction in the model, for identical output.

The CPU's instruction set

OpcodeNameMeaning
0HLTStop.
1LDA nAccumulator ← memory[n].
2STA nmemory[n] ← accumulator.
3ADD nAccumulator ← accumulator + memory[n], via the ripple adder (mod 16, carry flag = carry out).
4SUB nAccumulator ← accumulator − memory[n], via the same adder with inverted operand and carry-in 1.
5JMP nPC ← n.
6JZ nIf the zero flag is set, PC ← n.
7OUTAppend the accumulator to the output log.

An instruction is two nibbles — opcode, then operand — so the PC advances by 2 per instruction. The demo program is LDA 11 · ADD 12 · ADD 13 · ADD 14 · ADD 15 · HLT with 1, 2, 3, 4, 5 sitting in cells 11–15.

Every row is a pass. Two rows deserve a reading note. The ripple adder row: the bench adder is 4-bit and does have a carry-in, so it is proven two ways — all 512 combinations of (A, B, carry-in) at 4 bits, and the identical ripple core run at width 8 over all 256×256 = 65,536 operand pairs. Same function, two widths; both counts are printed, and neither is rounded into the other. And the CPU row checks more than the accumulator: the program must actually halt, and the data cells it read must be untouched afterwards.

Bends named honestly

Ideal switch transistors. The core's transistor conducts fully at base = 1 and not at all at base = 0. A real transistor has a threshold voltage, a partly-on analogue region, leakage when "off", and switching that takes time and energy. Real gates are also built from complementary pull-up and pull-down networks (CMOS), not a single pull-up plus a pull-down path. The bench keeps the one idea that carries the whole stack — a signal controlling a switch — and drops the analogue rest.

Latch settling is iterated evaluation. A real SR latch is continuous-time feedback: voltages chase each other around the loop in picoseconds. The core instead re-evaluates the two NANDs in turn until the outputs stop changing (at most 16 passes). For set, reset and hold that lands exactly where the real circuit lands.

The forbidden input, named. With S = R = 1 this model drives both outputs to Q = 1, Q̄ = 1 — an invalid state, because Q̄ is supposed to be the complement of Q — and in this iterated model, releasing back to hold afterwards leaves it sitting at 1,1. A real latch released from the forbidden state races: which side wins depends on picosecond asymmetries, and it can hang metastably before falling one way or the other. The model does not reproduce the race; it shows the invalid state plainly and does not pretend the outcome is defined.

Arithmetic is mod-16. Four bits wrap: 15 + 1 = 0 with carry out. The CPU keeps the carry flag so the wrap is observable, and the demo program was chosen to stop at exactly 15, but nothing in this machine detects overflow for you — exactly like the real small machines it is modelled on.

The GPU parallelism is a model of organisation, not real hardware concurrency. Your browser executes both the serial and the "parallel" versions one instruction at a time, underneath. What the wing models — truthfully — is the organisation: the same operation applied to many data items, lanes assigned to rows, and the step accounting that organisation implies (256 modelled steps vs 16). The proof that matters is the one the table runs: both organisations produce element-identical output, 0 mismatches over 256 pixels. On real GPU hardware the lanes really do run concurrently; the step counts here are the model's, stated as the model's.

One clock, no time. The CPU steps when you press Step, or in a tight loop on Run. There is no clock speed, no propagation delay, no memory latency. Timing is the next stack up, and this bench does not fake it.
