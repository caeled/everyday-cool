The NES Console — the lesson

A complete Nintendo Entertainment System that runs in a web page — and ships with no games at all. The console is the exhibit; the cartridges are yours, read from your own machine and never uploaded. Under the hood is JSNES, Ben Firshman's open-source JavaScript NES emulator, embedded unmodified. This page is the receipt: where JSNES came from, what was verified by driving the shipped page, and where the honest limits are.

▶ Open The NES Console

Where this one came from

Steven Powell's ROM library lives on a mapped drive at his house — homebrew NES games from his own shelf, and a collection built over years that, in his words, he “could play a lot of with a proper emulator.” The library cannot ship: those files are his, several are other people's work, and none of them belong in a public collection. So the commission split the problem the way the original hardware did. Nintendo sold a console and empty slots; the games travelled separately, in the owner's hands. On 2026-11-24 Steven commissioned three such consoles — this NES, the 2600, and the 6502 Bench beside them — each one the same shape: the page ships the machine, the player brings the cartridges.

The NES is the 6502's other famous home: its Ricoh 2A03 is a 6502 core with the decimal mode cut and a sound chip grafted on. Steven lived ten years with Atari programmer John Seghers; this machine speaks the family language.

What JSNES is

JSNES is a full NES in JavaScript: a 6502 CPU core, the PPU picture chip rendered to a 256×240 canvas, the pAPU sound chip (its audio worklet is generated from a Blob in-page — no file is fetched for it), controllers for two players, a light-gun zapper on the mouse, and save states that serialise the entire machine to JSON. The house page uses JSNES's own Browser cabinet class — canvas, speakers, keyboard, gamepad polling — and reaches the same NES object for the state codes. Cartridge boards supported in this build: mappers 0, 1, 2, 3, 4, 5, 7, 9, 11, 34, 38, 66, 71, 79, 94, 118, 119, 140, 180, 240, and 241 — the common boards, including MMC1 and MMC3.

The audit — a cartridge built to be caught lying

An emulator's word is worth nothing until a known program produces known pixels. The audit ROM is a synthetic fixture, written for this test and not shipped anywhere on the page: a 24,592-byte mapper-0 cartridge (sha256 622de8dc…8a) whose 6502 program paints nametable 0 with two solid tiles — a black top row over an azure field — and watches controller 1. One marker cell at row 2, column 2 flips to a red tile for exactly as long as the A button is held. Every expectation is a number, read off the shipped page's own canvas in a headless browser, driven through the page's own controls: the real file input, a real keyboard, the real buttons.

Field fix — 2026-11-24, later that day

The audit above was real, and it still missed the one path that mattered. On its first evening in Steven's hands, clicking Insert cartridge… on his own machine — tried in both Edge and Chrome — produced a flash and no file picker at all. The slot was a button whose only job was to call .click() in JavaScript on a file input hidden with display:none: a synthetic relay click on an invisible control. In Steven's browsers that relay went nowhere. The audit never caught it because it loaded its cartridge by setting the input's files programmatically — uploadFile() — which bypasses the human click path entirely. Steven's two browsers caught what eighteen green checks did not.

The fix removes the relay rather than repairing it. The slot is now a plainly visible file input, styled as the slot, with a <label> bound to it — the picker opens by the browser's own native activation, with no JavaScript between the player's click and the dialog, and the input itself can be clicked directly as well. Drag-and-drop is unchanged. Re-verification, this time through the human path: a trusted (CDP-dispatched) click on the label requests the file chooser; choosing the audit fixture through that chooser loads and renders it (azure field (60, 171, 255), black background); a trusted click on the visible input also requests the chooser; drag-and-drop still loads and renders; and the original 18-check drive still passes 18 / 18 against the fixed page — and again against the Baton Box's served copy, which carries the same fix (its inlined JSNES still extracts to sha256 b10b5f13…72d, byte-identical to upstream). The honest line stands: the first audit drove the input the way a script does, not the way a person does, and the person found it in one click.

Field fix #2 — 2026-11-24, that same evening

The fix above cured the click and missed the disease. Steven opened the fixed page, the picker now opened, he chose a cartridge — the input even showed its name, AV Poker.nes — and then: nothing. No game, no error, the status still reading “no cartridge inserted.” A second cartridge behaved identically. His cartridges were innocent — the same library plays in his RetroPie and RetroArch — and the reproduction pinned the fault in under a minute once the right environment was tested: every audit had served this page over HTTP from its own folder, engine beside it. Steven opens the page the way a person does — as a lone local file. In that environment the engine, loaded from a relative path (jsnes/dist/jsnes.min.js), simply wasn't there: ERR_FILE_NOT_FOUND, then ReferenceError: jsnes is not defined — and because the page's script built the emulator before it bound the cartridge slot, the whole script died at that line. No handler was ever attached. The picker and the filename beside it are the browser's own furniture, which is why the page looked alive while being dead. The first field fix's relay diagnosis was true of the code and still not the root cause: the relay had nothing behind it either.

The fix is structural, in three parts. (1) The engine rides inside the page. JSNES is now inlined into the HTML byte-for-byte (the same trick the Baton Box copy always used; the bytes still hash to b10b5f13…72d), so the page is one self-contained file that works served, saved, or opened alone — the pristine upstream copy stays in jsnes/ for the record. (2) The slot no longer depends on the engine to exist: the bootstrap is guarded, and if the engine ever fails to start the page prints that, in words, instead of sitting mute. (3) The console talks. Every cartridge is pre-flighted before the engine sees it — header checked, mapper read from the header the same way JSNES reads it — and every outcome prints a reason: not an NES image, a ZIP archive, a file too small, a read failure, an engine exception. The coverage case gets its own sentence, because it is the one a player must never mistake for a broken cartridge: the status names the mapper number and says the cartridge is fine — broader cores (RetroArch's Nestopia or FCEUmm) cover far more boards than JSNES's twenty-two. AV Poker's own board, for the record, is an American Video Entertainment NINA board — mapper 34 or 79 in the common dumps — and both of those are in JSNES's registry; a correctly headered copy plays here, and the re-verification drives a mapper-79 fixture to prove it.

Re-verification ran the matrix the first audits skipped: three environments (served over HTTP; opened as a file inside its folder; opened as a lone file with no folder — Steven's case) × hand-built fixtures on mappers 0, 1, 2, 4, and 79, an intentionally unsupported mapper 85, and a non-ROM text file, all chosen through the real file chooser. Supported boards boot and render in every environment (azure (60, 171, 255) at the test pixel); mapper 85 produces the printed coverage reason; the text file produces the printed header reason; picking the same cartridge twice in a row re-loads it (the input resets after each pick); drag-and-drop still loads; the original audit still passes 18 / 18; and the Baton Box's copy was regenerated from the fixed page and re-driven green. One more honesty item the matrix surfaced: opened as a local file, Chrome refuses JSNES's audio worklet module (blob:null/…), so a file-opened console may play silently — the game itself runs normally. The page now says that too, in a notice, the moment it happens, instead of letting a player wonder. The environment lesson, stated plainly for the next audit of anything: test the page the way the player actually opens it — an audit of the served folder is an audit of a room Steven never enters.

Field fix #3 — 2026-11-24, that same evening, twice more

Two more reports, both from Steven's hands on his own cartridge — Chip 'n Dale Rescue Rangers, one of his favourites, running at last. (1) Every control worked except B on the keyboard: Z did nothing, while the D-pad, X, Enter, and Ctrl all answered. (2) Pressing Reset mid-game crashed it — and the talking console from fix #2 earned its keep, printing the crash in the status line and the notice: “Game crashed, invalid opcode at address $9fd.” Both were real, both were ours, and both are fixed the same way: stop borrowing a mechanism whose failure mode is silence, and do the job in the page.

The dead Z. Steven's own testing split the fault before any tool ran: the on-screen B button worked — Chip picked up a crate beside him — so the B button constant and the emulator's input path were healthy, and only the keyboard layer could be lying. A hand-built readout fixture (eight cells in $4016 read order — A, B, Select, Start, Up, Down, Left, Right — each lighting as its bit arrives; sha256 085ac6d3…8cf) gives the evidence. In a clean profile, JSNES's shipped defaults bind Z correctly: the drive passes 21 / 21 — every printed key, both turbo keys, and all eight on-screen pad buttons, cells read off the canvas and cross-checked against the controller's own state. But JSNES's KeyboardController does not promise those defaults: its loadKeys() takes the key table from localStorage whenever a saved remap exists there, and the defaults are only the fallback. Seed a saved remap that is the default table with one entry missing — keyCode 90 — and the unfixed page reproduces Steven's evening bit-for-bit: Z dead (the B cell stays dark, the controller state holds 0x40), X fine, the on-screen B fine, 20 / 21 with the single failure at Z. That is the one page-reachable mechanism that kills exactly one printed key, and it is invisible from the page itself. The fix removes the whole class: the page binds the keyboard itself. JSNES's table is emptied so its handlers are no-ops, and the map the Help prints is asserted in this page's own code on every load — matched by code, then keyCode, then key, and delivered through nes.buttonDown/buttonUp, the very call the on-screen pad makes. Typing in the State Code box still types (form fields are left alone), browser shortcuts are left alone, and a window blur releases any held button. After the fix the readout drive passes 21 / 21 in a clean profile, 21 / 21 with the poisoned remap still in storage, 21 / 21 over HTTP, and 21 / 21 against the Baton Box's served copy. The printed map is now true by construction, not by default.

The Reset crash. This one is in JSNES's own source, in the gap between two functions. NES.loadROM() resets the machine, creates the cartridge's mapper, and then calls the mapper's loadROM() — the step that loads the PRG banks, refreshes the CPU's PRG read path, and requests the reset interrupt. NES.reset() — all the old button called — creates a fresh mapper and never runs that step. A cartridge whose banks sit in their power-on arrangement survives the omission; an MMC1 game mid-play, its banks rearranged by serial writes, restarts into unloaded windows and executes garbage until it wanders into RAM and dies — at $9fd, in Steven's case. Reproduction, not just reasoning: a hand-built MMC1 fixture (64 KB; bank 3 boots the healthy azure field; pressing Start serial-writes PRG bank 2 into the low window, the in-game state; bank 2 carries a red “wrong bank” payload) driven through the old handler crashed on the first Reset from the bank-switched state with Steven's exact message — invalid opcode at address $9fd — the address included. The fix is the same shape as the keyboard's: the page kept the cartridge's bytes when it loaded, so Reset now re-runs the whole load path (browser.loadROM) instead of borrowing the core's soft reset — a cold restart, a power cycle with the cartridge left in, and the Help says so in those words. Verification: the MMC1 fixture, Start pressed, Reset five times — the opening frame returns every time and no crash prints — on the standalone file (7 / 7) and over HTTP (7 / 7); the mapper-0 audit fixture resets five-for-five in both environments (6 / 6 each); the original audit still passes 18 / 18; and the Baton Box's copy was regenerated from the fixed page and re-driven (buttons 21 / 21, MMC1 resets 5 / 5). The one recurring error line in these drives is the known file:// audio-worklet refusal from fix #2 — the game plays silently, the page already says so, and it is not a crash.

The challenge baton, measured

State Code ≈ 851,000 characters · Relay Code ≈ 1,500 characters An NES state is the whole machine — CPU, picture chip, cartridge board, sound, controllers — so a baton pass here is roughly 570 Relay Codes of text. It fits the Baton Box contract's ~1 MB blob guidance with little room to spare: paste it, don't retype it. The same cartridge must be inserted before import; a state is a moment from one specific game, not a game in itself. This console is registered on the Baton Box (passenger: the-nes-console, state name “State Code”) — and the registration was proven, not just filed: the box served its copy of this page and the full audit drive passed against that copy too.

Because the Baton Box serves single files, its copy of the console page carries the JSNES library inlined. That copy was verified mechanically: the inlined bytes extract to sha256 b10b5f13…72d — byte-identical to the upstream jsnes.min.js the collection page loads. Same emulator, two envelopes.

Honest notes

JSNES is a solid, simpler core — not a cycle-perfect one. It emulates the CPU, PPU, and sound in frame-sized strides rather than chasing every cycle the way the accuracy-first emulators do. The vast middle of the library plays correctly; games that lean on exact mid-scanline timing tricks, split-screen raster effects timed to the cycle, or oddball cartridge boards outside the mapper list above can glitch, desync, or refuse. That trade is upstream's design — a NES that runs anywhere JavaScript does — and this page inherits it knowingly.

A restored state can hold a button down. States carry the controllers, by design — it is what makes a mid-jump handoff honest. It also means an imported moment may begin with a phantom A press until the next real input clears it. The audit met this head-on and it is printed here rather than smoothed over.

The one console warning in the drive was the audit's own. Chrome suggested a readback optimisation because the audit reads pixels with getImageData; a player who never inspects the canvas never sees it. Errors were zero.

No ROMs were harmed, shipped, or downloaded. The only cartridge in this entire build is the synthetic audit fixture, which lives with the audit notes, not on the page. Steven's library was never copied, listed, or touched — the slot reads a file the player picks, on the player's machine, full stop.

The public shelf — added 24 November 2026

Both cartridge consoles gained a second door the same evening: a public shelf block directly under the slot, pointing at the Internet Archive. Three starter titles stand on this console's shelf — the public-domain Micro Mages demo and its Second Quest (one Archive item, micro-mages, carrying both bare .nes files), and The Legend of Zelda (zelda_nes_2) — and a paste-a-link field resolves any Archive item page to its cartridge files through the Archive's metadata API. Steven's direction, and the house rule survives intact: the Archive hosts and serves the cartridges; this page hosts none, downloads none, and keeps none.

Why the shelf is a door and not a slot — the CORS evidence. The Archive's metadata API answers any page: it sends Access-Control-Allow-Origin: *, so resolving an item link works from this page today. Its file servers send no Access-Control-Allow-Origin header at all — traced end-to-end, on the /download/ redirect and on the file response alike — and a browser may not hand a page bytes it was never given permission for. So the cartridge bytes cannot be fetched into this console, on any of the consoles, until the Archive changes that one header. Relaying the bytes through a server of ours would defeat the wall and the rule at once — we would be re-serving other people's cartridges — and was named and declined in the feasibility pass.

The interim form, and the upgrade path. As shipped, the shelf's buttons and every resolved cartridge open the Archive's own player page for the item, in a new tab — the same file, read in their house. The block is built so that exactly one function is the hand-off: the day the file servers send the header, that function alone changes — fetch the bytes, hand them to the same loadROM path the local slot uses — and the parsing, the file list, and the failure sentences (not a cartridge; a zip this console can't open; a cartridge for a different machine; an item with no cartridge in it) stay exactly as they are. The console itself is untouched: the audit's zero-network story still describes the machine; the shelf speaks to the Archive only when a visitor uses it, and the page's Help says so.
