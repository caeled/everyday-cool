What is this?

A working DOS machine in the left panel, and the walkthrough for setting up TCP/IP on it in the right panel. You type every command yourself, at the machine's own prompt. Nothing is simulated: the packet driver is a real 1995 Realtek driver, the TCP/IP stack is the real mTCP, and every message quoted in the walkthrough is the message the programs actually print.

Using the machine

  • Click the black screen to give it your keyboard, then type at the C:\NET> prompt.
  • The machine boots itself when the page loads. The Restart the machine button under it starts the drive over, clean.
  • Tick each stage's box as you finish it — the ticks are kept in this browser, on this machine only.

The one honest limit

This console's machine is an emulation, and the emulation has no network card fitted. The workshop is built around that fact rather than despite it: the driver will tell you the card is not there, in its own words, and learning to read exactly which layer is speaking is the skill being taught. The same drive, in an emulator that fits a card (DOSBox-X) or on real hardware, completes the setup live — driver loads, DHCP takes an address, PING answers.

The Network Card — TCP/IP under DOS, one layer at a time

A plain DOS machine. A network card has been fitted — an NE2000-compatible card, the kind nearly every machine of the era had or pretended to have. Nothing is loaded: no driver, no stack, no address. Bringing the network up is the job, and the walkthrough sits right beside the machine: read the step, type it, read what the machine answers. That is the whole format — and it is how it was actually done.

Where this pack came from. The drive is modelled on Steven Powell's own working DOSBox C: — “the basic C I would build” — and the components are the ones he fetched the way techs always did: the packet driver and the Crynwr collection preserved on archive.org, the mTCP stack from its author's site, Trumpet Winsock noted for the Windows layer. Assembled and audited by Muse; every quoted message in the walkthrough was captured from these very programs running in this very console.

The walkthrough

Eight stages. Work down the list; the machine on the left is waiting at each one.

1 · Meet the machine

The machine boots itself and lands at a prompt in C:\NET — the one folder this job needs. Look at the toolbox:

DIR

Every file the setup needs is in this folder: the driver, the utilities, the configuration, and a complete TCP/IP stack. Nothing to install, nothing to fetch — a tech's drive, laid out before the work starts.

2 · Read the map

TYPE README.TXT

The drive's own notes: what each piece is and why it is here. Read it the way you'd read the last tech's handwriting in a machine you're taking over — because that is what it is.

3 · Load the packet driver

DOS programs cannot talk to a network card directly. The first layer is a small driver that sits between them and the hardware, at software interrupt 0x60. Load it:

PNPPD 0x60

The driver introduces itself — and then reports, in its own words:

Packet driver for RTL8019, PNP version 1.31 Copyright 1995 (c), Realtek Semiconductor Inc. There is no 8019 PnP card on your system !

That is not a failure of your typing. The driver probed the machine for the card and the card is not there — this console's emulation doesn't fit one. Hold the shape of the moment: the driver is fine, the software is fine, and the layer that is missing is the hardware. On a machine with the card, this same command ends with the driver resident at 0x60, and everything above it can start.

4 · Interrogate the machine

Don't take one program's word. Ask the machine what packet drivers it can find, at any interrupt:

PKTTOOL SCAN
Scanning: No packet drivers found - did you load one?

Two witnesses, one story: nothing is loaded, anywhere. This is the diagnosis habit the whole workshop is for — when a layer misbehaves, ask the machine, don't guess.

5 · Read the configuration

TYPE MTCP.CFG

The stack reads this file before it does anything. Three things to see in it: packetint 0x60 — the stack will look for its driver at 0x60, so the config and the driver must agree about the address, or nothing above matters; the machine's hostname; and the choice between asking the network for an address (DHCP) or setting one statically, in the commented block. A configuration file is a promise the rest of the system makes — this stage is reading the promise before testing it.

6 · Ask the network for an address

DHCP
Init: Could not setup packet driver, are the configured interrupts correct? Configured packet driver interrupt: 0x60 Could not initialize TCP/IP stack

The stack refuses to start, and notice what it does: it asks you a question, and the question is the method. Are the configured interrupts correct? You already know the answer from stages 3 and 4 — the config is honest (0x60, as written), and there is no driver there for it to find, because there is no card under the driver. Each layer's complaint points one layer down.

7 · Test anyway

PING 1.1.1.1
mTCP: 'IPADDR' must be set.

One line, and it's the address layer speaking: this machine has no address, because the program that fetches one couldn't run, because the stack couldn't start, because the driver couldn't load, because the card isn't fitted. A five-link chain, and you can now walk it in both directions. On a machine with the card, DHCP writes the leased IPADDR into MTCP.CFG — and this same PING goes out and comes back.

8 · Read the whole board

The layers, in the order you met them: card → driver → configuration → stack → address. Every network fault you will ever meet lives in one of them, and the craft is hearing which one is talking before touching anything. The modern world adds one more layer on top — the network itself, and the control daemons that run it. DHCP is one of those daemons: the address in stage 7 arrives by grace of a service elsewhere. When a daemon lies or dies, every correctly-built machine is wrong together — the one failure your five layers can't fix from inside the machine. The lesson page tells the rest of that story, including the Windows layer (Trumpet Winsock, and why there must only ever be one WINSOCK.DLL) — the file TRUMPET.TXT in this machine is the start of it.

The honest box

The machine is DOSBox (by way of js-dos, GPL) running on this page; your keystrokes never leave your computer. The drive is real period software, not a re-creation: Realtek's PNPPD packet driver (1995), utilities from the Crynwr packet driver collection, and Michael Brutman's mTCP — a living, maintained TCP/IP stack for DOS, included under its GPL licence (COPYING.TXT is in the machine). The one thing that is not real is the card: this emulation fits no network hardware, and the workshop says so on its face and teaches around it. Run the same drive where a card exists — DOSBox-X fits an NE2000 — and stages 3, 6 and 7 complete live.

The pack itself is shareware in the old sense — the note is inside the machine, in REGISTER.TXT, where it belongs. The lesson page carries the audit: how this workshop was verified, keystroke by keystroke.
