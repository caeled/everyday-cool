Nerd Heaven · The back door to The DOS Console

The DOS Console — the lesson

A whole DOS PC in one web page — and it ships with no software at all. You bring the drive: zip the folder you keep as a C: drive, mount it, and take the prompt, the way DOS people have always worked. Under the hood is DOSBox Pure, a fork of DOSBox, running inside the EmulatorJS frontend — both embedded unmodified, both licenses carried with the page. This page is the receipt: where they came from, the license reasoning in plain words, what was verified by driving the shipped page, and the honest limits — including the one requirement, printed on the console's own face, about where this machine is allowed to switch on.

▶ Open The DOS Console

Where this one came from

Steven keeps a DOS archive the way he keeps everything: one prepared folder that is a C: drive, mounted in DOSBox whenever he wants that world back — Oregon Trail included; it is a game he pulls up in DOSBox all the time. When the console shelf in Nerd Heaven reached its fifth machine, his commission was one line: “if it has a dosbox core add that to our emulator page with the load function. Golly I have a whole dos archive.” Then he specified the shape himself, and the shape is his habit, not a product manager's: Mount your C: is the primary door — the console boots to a working C:\> prompt with no forced auto-run — and the single-game zip with a Run command is the second door. A window-size option and a pop-out followed in the same conversation, because some DOS screens are small to play in. The third door, the Internet Archive's MS-DOS shelf, shipped in the interim form the Archive's own headers dictate; that story has its own section below.

What DOSBox Pure and EmulatorJS are

DOSBox is the long-lived open-source DOS emulator: a PC with its own DOS-compatible shell, built to run the software of the DOS era. DOSBox Pure (by Bernard Schelling) is a fork restructured as a libretro core — the plugin shape the EmulatorJS frontend loads — with a game-first front end: a start menu for loose executables, on-the-fly disc handling, and a documented behaviour this console leans on, described and then corrected by measurement in the mount section below. The frontend is EmulatorJS 4.2.3, the same stable line, and the same vendored rack pattern, as the SNES Console beside it.

One naming fact worth recording, because the package shelf is confusing about it: there is no @emulatorjs/core-dosbox package (the registry answers 404). The frontend's own source maps its "dos" core key to dosbox_pure, and the real package is @emulatorjs/core-dosbox_pure@4.2.3. That is the package in the rack — established from the registry and the frontend's code, not from memory.

The license question, in plain words

This shelf's rule is the same as the SNES gate: an authoritative build, a license that fits a personal non-commercial collection on its face, attribution carried prominently, files unmodified. DOSBox Pure clears it more easily than Snes9x did. DOSBox, and DOSBox Pure with it, are under the GNU General Public License, version 2 or later — the author's own README says so, and both core payloads carry the GPL-2.0 text embedded inside them; that embedded text is vendored in the rack as LICENSE-dosbox-pure-gpl-2.0.txt, byte for byte what the payloads ship. The EmulatorJS frontend is GPL-3.0; its license is vendored beside it. GPL software may be copied and shared with its license and attribution intact, which is exactly the arrangement here. And the standing rule of the whole shelf holds: the machine ships, the software doesn't — no DOS programs are in this build, not Steven's, not the Archive's, not a test game. The only DOS program in the entire audit is the hand-built fixture below, and it lives with the audit, never on the page.

The audit — a program built to be measured

An emulator's word is worth nothing until a known program produces known pixels. The audit fixture is TEST.COM: 250 bytes of hand-assembled 8086 (sha256 81e71912…), built for this console and never shipped. It paints the screen white-on-red and prints DOS CONSOLE FIXTURE READY; on a capital A it repaints white-on-green and prints KEY A RECEIVED — FIXTURE OK; on any other key, white-on-blue; on a second keypress it exits to DOS. Every stage is a different full-screen colour, so a screenshot is a measurement, not an impression. The page was driven headlessly against a local server, through its own pickers, buttons and keyboard path — never by calling the emulator's internals.

Door two first (one game, straight in). The fixture zip (audit-game.zip, sha256 7f530ec9…) went through the game picker; the page found TEST.COM, prefilled the Run command with it, and booted. Stage A measured exactly as built: dominant colour (170, 0, 0) — DOS bright red — with the fixture's two lines on it. A held capital A (see the keyboard section for why “held” matters) turned it (0, 170, 0) green, “KEY A RECEIVED — FIXTURE OK.” A further keypress exited to a C:\> prompt printed over the stage — the program had run, branched, and returned, start to finish.

Door one (Mount your C:) — the primary door, driven the way Steven works. A fixture drive zip (audit-cdrive.zip, sha256 5ec3f8a3…: a NOTES.TXT at the root, the fixture at GAMES\TEST\TEST.COM) went through the Mount picker and booted straight to the prompt — DOSBox Pure's welcome, the mount line, the console's own greeting, then C:\>. At the keyboard, in order: DIR listed NOTES.TXT and GAMES; CD GAMES\TEST moved the prompt to C:\GAMES\TEST\>; DIR listed TEST.COM, 250 bytes; TEST ran it — red, then green on A, then out — and the prompt that came back was C:\GAMES\TEST\>. Mount, navigate, run, react, exit: the whole habit, in the page.

The request log. Across a full local session the page made 19 requests. Eighteen are this page and its rack, from the same origin. The nineteenth is the one outside call in local mode, and it is upstream's, not the console's: EmulatorJS's own version check (cdn.emulatorjs.org/stable/data/version.json), which its code only attempts when the page is served from a localhost address — the same fenced phone-home the SNES lesson records. It carries nothing of yours; no file name, no zip, no state ever leaves the machine. Console errors in local mode: two, both accounted for — the browser asking for a favicon.ico this page doesn't declare (a 404, cosmetic), and, inside the audit's sandboxed network only, that version check failing to tunnel out. On an ordinary connection the check simply succeeds, silently.

The refusal sentences were driven too. A text file renamed .zip: “That file isn't a zip…” A real zip with no program in it: “No program in that zip — no .EXE, .COM or .BAT for the Run command to run. If it's a whole drive rather than one game, Mount your C: is the right door,” and the Run box stayed hidden. A catalogue lookup for an identifier that doesn't exist: “That item didn't resolve…” And when the catalogue couldn't be reached at all — which the audit sandbox arranged for real, by refusing the browser's tunnel to archive.org — the page said that, in those words, instead of spinning. Every failure gets a sentence; that is the house style and it held.

How the boot works — the generated CONSOLE.CONF

DOSBox Pure's core declares exactly one content extension it can be handed: conf. So the console never hands it your zip. In your browser, the page reads your zip's directory, rebuilds it with its entries' compressed bytes transplanted untouched, and adds one small stored file first — CONSOLE.CONF — whose [autoexec] mounts the drive and either stops at the prompt (Mount mode) or runs your command (game mode). Nothing is uploaded; the rebuild happens in the page, and zips it can't honour — ZIP64, multi-disk, encrypted entries — are refused with a sentence rather than mangled. If your zip carries its own dosbox.conf, the console's file still wins the boot, because it is the one EmulatorJS is told to load; your file rides along as an ordinary file on the drive.

The mount that isn't automatic — a documentation bend, corrected

DOSBox Pure's own README says that when a .conf file is loaded as the content, Pure “will mount the directory of that file as the C: drive and then use it.” In the EmulatorJS flow, measured: it does not. The first audit boot ran the conf's autoexec with no drive mounted at all — C: answered “Drive C does not exist! You must mount it first,” and the Run command was an illegal command at Z:\>. Whatever directory Pure would have mounted in its home frontend, in this loading path the mount simply never happens. So the generated conf mounts the drive itself, with the same command a person types: MOUNT C / — the zip's contents are extracted at the frontend's filesystem root, and that root is the drive. DOSBox answers with its standard red warning, “Mounting / is NOT recommended. Please mount a (sub)directory next time” — honest machine noise, visible for a moment at every boot, left in rather than hidden. The DIR listings in the audit are the receipt that the mount lands.

Two honest consequences of that geography. Your drive's root is shared with the machine's own working folders — a DIR shows DATA, DEV, HOME, PROC, SHADER and TMP beside your files. They are the frontend's furniture, they don't touch your files, and DOS people will recognise the arrangement: every mounted drive has something of the machine in it. And the boot file itself appears in listings as CONSOL~1.COM — DOS's 8.3 truncation of CONSOLE.CONF as Pure's directory code renders it. Cosmetic; noted so nobody diagnoses it.

The threads requirement — where this console can switch on

The DOS core ships only threaded builds (its build report says requireThreads: true), and a threaded core needs SharedArrayBuffer, which a browser exposes only on a cross-origin isolated page: the server must send Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp, on a page the browser treats as a secure context. The SNES core had a non-threaded fallback and could run anywhere; this one cannot, and the console says so on its face rather than failing quietly. Measured and ruled, environment by environment:

Where the page standsVerdict
Local server sending both headers, opened as localhost / 127.0.0.1 Runs — this is the audit environment; every measurement on this page was made there.
Same server, headers not sent Refuses, in plain words — the status line carries the explanation on load and after a boot attempt; no boot is started. Driven and read back.
A lone file (file://), like the NES console's home turf Cannot run — no server, no headers, no isolation. This rack is a folder, not a single file; it was never going to live there.
GitHub Pages (this collection's web home) Cannot run as Pages serves today — Pages doesn't let a site set those two headers. Wiring this console to the live site is therefore a display decision, not a working one, until the serving changes; nobody should wire it expecting it to boot there.
Plain http on a LAN address, headers sent Still cannot — an http LAN address is not a secure context, so the headers alone don't isolate. (Stated from the platform rule; the audit sandbox's own LAN address is unreachable even to itself, so this one cell is ruled, not measured.)
https with both headers, anywhere Runs — the same rule, satisfied the other way.
The Baton Box Runs — and it is this console's playable home. At Steven's direction (24 November 2026, “Serve DOS from the Baton Box”) the box was patched to serve game folders whole and to send the two headers (plus Cross-Origin-Resource-Policy: same-origin) on its game routes. Proven against the patched box itself: it served this console, a headless drive booted the fixture drive zip to C:\>, worked the prompt, and ran the fixture (red → green → back at the prompt), with the browser reporting crossOriginIsolated: true. The box's own lesson carries that update's full receipts.

The picture that folded to zero — this build's big bend, and its fix

The audit caught the vendored frontend in an intermittent failure nobody's documentation mentions. EmulatorJS sizes its canvas by fitting it into its container box when its resize handler runs. If a refit lands while the box is at a transient near-zero height — mid-boot, mid-move — the fit can latch: the canvas ends up 840×0, a black strip where the picture belongs, and it never recovers. Reproduced in the harness at roughly one boot in two before the fix. The non-cures were measured too, so nobody wastes time on them: calling the frontend's own resize handler doesn't cure it, a window resize doesn't, and cycling the size setting refits the width and leaves the height at zero. Once latched, only a reload saves the session.

The fix is structural, and it is house code only — no upstream file touched. The console's screen box carries aspect-ratio: 2/1 in the page's CSS, so its height derives from its width and can never be near zero at any moment a refit might sample it; the poisoned fit has no poisoned input to eat. The page also calls the frontend's resize handler once more after every size, pop-out, pop-back and fullscreen change, as belt and braces. After the fix: six of six looped boots clean, and every audit drive after it clean — where before, one boot in two folded. The same frontend serves the SNES Console; whether its box needs the same guard is a fair question for that page's next audit, and it's recorded here so it gets asked.

The keyboard, measured

DOS is a keyboard world, so the map was measured at the prompt and in the fixture, not copied from a chart. What the shipped console delivers: letters, digits, space, Enter and Backspace type as printed; the prompt drives exercised DIR, CD GAMES\TEST (the backslash is its own key), paths with a colon (Shift+;), and program names, all landing as typed. Capitals deserve their sentence: a held Shift works — measured two ways, a human-timed Shift+A and CapsLock+A, both delivered the fixture's capital-A branch. The audit's first attempt at A, a synthetic Shift+A pressed and released inside a few milliseconds, arrived as a plain a and took the other branch — DOS samples the shift state, and a shift that brief can be missed. That is a property of fast synthetic keys, recorded here so nobody re-diagnoses it as a broken keyboard; a person's held Shift is not that fast. The console's own notes bar says the working rule: click the screen, then type — DOS reads your real keyboard.

The challenge baton, measured

Like its siblings, the console wraps the frontend's own state in a copyable code — prefix DOSSTATE1: — and this core's states are practical in a way the SNES's weren't. Exported at the fixture's green stage: a code of 196,650 characters (147,480 bytes of machine) — a sixth of the SNES console's 1,097,923, comfortably inside the Baton Box's size guidance. The round trip was driven: export, let the machine move on (the fixture exited; the prompt came back), import — and the screen returned to the exported stage, pixel for pixel in distribution, with the page's words: “State restored. The machine is exactly where the last player left it.” One boundary, printed on the console itself: the code carries the machine — memory, processor, screen — not your drive's files, which live outside the core's state. The next player mounts the same drive zip first, then imports. A baton for the machine; the drive travels the way drives always have, as a folder.

The Archive door — the shelf is theirs

The commission's third door wanted Oregon Trail loaded from the Internet Archive. The feasibility question was settled at the header level before a line of the door was built, and re-verified first-hand during this audit. The Archive's metadata API is open to web pages — it answers with Access-Control-Allow-Origin: * — and the item is pinned exactly: msdos_Oregon_Trail_The_1990, “Oregon Trail, The” (1990), its game file Oregon_Trail_The_1990.zip, 359,527 bytes. But the Archive's file servers send no Access-Control-Allow-Origin header — checked through the whole redirect chain to the file host — so a browser page cannot fetch the software itself across origins today, on this console or any other. Fetching anyway would fail silently; relaying the bytes through another server would make this page a mirror, which the shelf's rule forbids. So the door ships in its interim form, and says so on its face: the button (and the paste-a-link field for any other item) resolves the item in the Archive's catalogue, then opens the Archive's own player for it in a new tab — the shelf is theirs; the reading happens in their house. The day their file headers open, the same button becomes a load-here button with no redesign; the door's shape doesn't change, only where the bytes land.

What the audit could and couldn't prove about that door, plainly: the resolve-and-open logic was driven end to end — the Oregon Trail button opens exactly archive.org/embed/msdos_Oregon_Trail_The_1990 and reports the item's real catalogue title; a bogus identifier gets the miss sentence; an unreachable catalogue gets the unreachable sentence (that branch fired for real in the sandbox). The Archive's player itself could not be rendered inside the audit sandbox — its network refuses the browser's tunnel to archive.org while happily serving the same addresses to a command-line client — so this lesson makes no claim about the title screen. That receipt belongs to the first click on an ordinary connection, and the door is honest about being theirs in the meantime.

The mount that failed in Steven's hands — and the folder door (26 November 2026)

What happened. Steven installed the Emulator Box app, opened this console, and picked his real C: archive — a zip he knows is good, because desktop DOSBox mounts it. The page refused it: “The zip couldn't be read: The requested file could not be read, typically due to permission problems that have occurred after a reference to a file was acquired.” A copy moved to a local folder failed the same way; so did a copy with its permissions opened up. Stock answers, all three — and all three wrong, because the file was never the problem.

The diagnosis. The page read the whole archive in a single file.arrayBuffer() call. In the app's WebView2, that one-shot read of a very large file is refused outright, with exactly that misleading permission sentence. Driven headlessly, the same page mounted a 42 MB test archive without complaint — the failure lives in the one-shot read in his environment, not in his archive and not in the zip format.

His correction, which was right: DOSBox doesn't make you zip anything — it mounts a folder. The zip requirement made the console harder than the machine it emulates. The zip existed because a web page cannot see a folder path; but a directory picker hands the page the folder's files with their relative paths, and that turns out to be enough.

The fix, shipped the same morning. (1) Every read on both doors is now sliced — 16 MB chunks instead of one gulp — and the read starts before the picker is cleared. (2) Door one gained a second key: “…or mount the folder itself…” — pick the drive folder and the page builds the same boot drive from its files in memory (stored uncompressed, the same generated CONSOLE.CONF added), nothing uploaded, the folder on disk untouched.

The audit. Both doors driven headlessly against a 42 MB test drive (seven files, one of them 36 MB): the zip door reached the DOS prompt in about six seconds; the folder door in about four — DOSBox Pure parsed the page-built folder zip, mounted it, and presented the prompt, which is the receipt that counts. The closing receipt is still Steven's: his own archive mounting — under the engine swapped in the same morning, in the section below, which needs no app and no box.

Field use: the reading room (26 November 2026)

Steven's note, watching his own archive walk in: a console like this is not only for games. Point the folder door at a folder copied off a real machine's C: drive — an old disk read through a USB adapter — and the whole tree stands up at a DOS prompt, openable by the very programs that wrote the data. That is a support instrument, not an exhibit: half of data recovery is finding a reader old enough to understand the files. So the console grew its fourth door the same morning: Rescue files. List what is on the mounted drive (the engine's own filesystem tree), tick the files, and the page reads them back out and builds a zip in the browser for download — the virtual F: drive, wearing web clothes. The audit's receipts: the test drive listed its skeleton's five files honestly (the deferred WAD was not yet in the machine, and not listed); after the GAMES folder was loaded from the lazy panel, the list grew to six, and the rescued DOOM1.WAD and AUTOEXEC.BAT came out byte-identical to the source drive. The boundary, printed on the door itself: it rescues files from a readable copy — a physically dying disk needs its imaging step first. The console is the reading room, not the ambulance. Steven's summary of the whole exhibit stands as this section's receipt: "a game as a lesson that turned into a tool… a full DOS emulator and a tool you can use to recover data — for Nerd Heaven."

The size wall, and the streaming door (26 November 2026)

Hours after the swap, Steven tried to mount his whole archive at once: the C: folder zipped, 2,220,069,881 bytes. The player answered "offset is out of bounds" — and the number is the whole diagnosis. A browser will not hold a single file buffer past 2,147,483,647 bytes (231 − 1); his zip was 72 MB past that line. The old folder key had the same wall hidden inside it: it read every file, then built one bundle out of all of them, so the drive had to fit in the browser twice over. No setting raises that ceiling — it is the browser's, not the page's.

So the folder key stopped bundling. It now boots the machine on a conf-only bundle — an empty drive and a prompt — and then copies the picked folder into the running machine file by file, streamed (the player's own fsWriteFile, fed from each file's stream), so nothing is ever held whole. One wrinkle, measured: DOSBox caches its drive listing at mount time, so files that arrive after the mount are invisible to DIR until the cache is cleared — DOS has a word for that, RESCAN, and when the copy finishes the console types it itself. The audit trail: the 42 MB test drive streamed in through the shipped page's own folder door, the screen showed the page's typed rescan answered by "Drive cache cleared.", and the prompt that followed listed every streamed file. The ceiling that remains is the honest one: the drive lives in the machine's memory, so a drive needs roughly its own size in free memory — gigabytes are fine on a machine that has them. The zip key keeps the bundle route and its one-piece limit, and now says so in plain words before it tries, pointing at the folder key — which is where a whole archive belonged all along.

The lazy drive (26 November 2026, later still)

Steven's refinement, in his words: "load the directory of the big C, then only load a subfolder if needed — that would manage it the way DOS did." He is right about the principle: DOS never loaded a drive; it read the disk when a program reached for something. A web page cannot intercept DOSBox's reads, so the console now does the honest version of the same shape. The folder key partitions the picked drive into a skeleton — every folder, every file up to 256 KB, and each folder's smallest file, so no folder arrives empty — and the rest, grouped by top-level folder. The skeleton streams in first and the prompt is live in seconds, the whole directory tree walkable by DIR and CD. The big folders wait in a panel under the screen with their true sizes; each Load button streams just that folder in, followed by the console's own typed RESCAN. The audit drove the shipped page: the 42 MB test drive arrived as a skeleton with two deferred groups — the drive root's 36 MB data file and the GAMES folder's WAD (its DOOM.EXE, the folder's smallest file, rode the skeleton) — the panel's real Load button streamed the WAD in, the DOS screen showed two rescan cycles, each answered "Drive cache cleared.", and the unloaded file stayed out until called for. The named bend: until a folder is loaded, DOS sees it as an empty folder — the panel, not the DIR, is the truth about what is in. One more piece of furniture, added at Steven's word the same morning: picking a folder can make the browser show a large "upload" confirmation — his count was 47,191 files — and startup on a big drive takes a minute or two, so the folder button now warns first, in a panel carrying his own text: "With a larger drive start up may take a minute or two, and you may get a browser message about uploading a lot of files. What it is doing is uploading the directory into the VM that runs the emulator. No files are copied off your machine." Warn about the warning, before it happens.

The counted load \u2014 a guard on the lazy drive (26 November 2026)

The lazy drive's first full field run was Steven's own: he picked his whole archive, pressed Load everything, watched the completion line print \u2014 Everything is in \u2014 and then could not get control of the machine again. No click landed, no key typed. Reproduced here in miniature, small drives load and type perfectly after panel loads, and the page's own code had plainly finished (the completion line is the last thing it prints). What had died was the emulator underneath, carrying some two and a half gigabytes in its memory: this engine dies silently when its memory runs out, and a dead machine inside a living page reads exactly like a freeze.

The fix is that loads are now counted. The lazy panel keeps a running total \u2014 In the machine so far: X of Y on this drive \u2014 and any load, one folder or everything at once, whose projected total would pass 1.5 GB stops before it starts, says why in plain words, and re-labels its own button \u2026anyway: a second click loads it regardless. Nothing is blocked and nothing is decided for the visitor; the load just asks once, the way the folder door asks before the browser's upload warning. Clicking the screen also now hands the player's canvas the keyboard focus explicitly, so typing has a definite home.

Audit receipts: an ordinary load runs untouched (the total line read 493 KB of 40.5 MB at the skeleton and 4.5 MB after GAMES); with the counter forced past the line in a test rig, the first click printed the warning, re-labelled the button, and loaded nothing, and the second click loaded the folder; a click on the screen lands focus on the canvas; no page exceptions. One honest footnote: the first guard test appeared to fail because the test itself set 1,600,000,000 bytes against a 1.5 GiB line \u2014 1,610,612,736 bytes \u2014 and the guard, correctly, did not fire. The test was wrong, not the guard; units are a diagnosis too.

The engine swap — DOS that runs anywhere (26 November 2026)

The morning the folder door shipped, Steven did what the lesson above had been asking him to do: he opened the console in the Emulator Box app and tried to mount his archive. The read fix worked — his DOOM.zip parsed, its programs were found — and then the machine refused to switch on, because the app's window, like GitHub Pages and like a lone saved file, is not a cross-origin isolated room, and DOSBox Pure ships only in a threaded build that needs one. The Baton Box could serve the console with the right headers, and by the end of the morning it did — but Steven's verdict on the whole arrangement was the design correction this exhibit needed: if he has to run a server, copy addresses, and pick the right window, no learner and no teacher will ever get this far. A console a classroom can't switch on is not a console.

So the engine was swapped, the same operation the SNES Console went through the night before. Out: DOSBox Pure via EmulatorJS (threaded, isolation-bound). In: DOSBox via the js-dos player (v8.5.4, GPL-2.0, vendored unmodified in jsdos-dos/ — the pairing that serves DOS games to the whole internet at dos.zone). This DOSBox build is not threaded, so it needs no isolation, no headers, no server: the page boots standing anywhere a page can stand, including inside the app window itself. The Baton Box goes back to its real job — passing games between people — and the State Code door went with the old engine: the player's own save button keeps a session now, because saving was always the machine's job, not the player's.

What the swap changed under the doors: the page now packages your files as a js-dos bundle (.jsdos) — your files plus one small written-by-the-page .jsdos/dosbox.conf whose first commands mount the package as C: and hand over the prompt. Honest notes

The boot settings are the console's, stated: the generated conf sets machine=svga_s3, memsize=16, cycles=auto. Sixteen megabytes and an S3 card is a generous late-DOS machine; software that wants a slower, older box can be given one by editing the conf the page generates — a v2 nicety, not hidden, just not built.

DOSBox Pure is a games-first fork. It runs the era's software with a DOS-compatible shell of its own — not a byte-exact IBM DOS, and not trying to be. For period-exact archival work the desktop DOSBox line remains the reference; for a drive full of games and the prompt they lived at, this is the machine Steven asked for, measured doing exactly that.

The picture's proportions are the frontend's choice: DOS text (720×400) is presented in a 2:1 canvas with the picture centred — glyphs render a touch wide next to a period CRT's 4:3. Upstream's presentation, unmodified, noted rather than corrected.
