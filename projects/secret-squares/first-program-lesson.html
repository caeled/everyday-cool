First Program — the lesson

First Program is a tiny computer that speaks a tiny BASIC, built so you can watch it work: the line being read lights up, the variables sit in named boxes where you can see them change, and the output arrives one statement at a time. This page is the other half — what a program is, why the machine can only ever be told the things its dictionary holds, why the same program runs the same way every time, and how this one is built, with the receipts from its own proof runs — readable while you play, from the 📖 Lesson button in the game.

A program is a text that does nothing

Type 10 PRINT "HELLO" into a notebook and nothing happens. Type it into the machine and a word appears. The text was never the doing — the text is a score, and a program only exists when something reads the score and obeys it, one word at a time, in order. That reader is the interpreter, and everything on the bench is arranged so you can watch it read: it has exactly one place it is looking (the lit line), exactly one set of things it remembers (the boxes), and exactly one thing it has said so far (the output). A running program is not a mystery unfolding. It is a reader, a place, and a memory — all three on the table.

The dictionary is the machine's entire vocabulary

The bench's left panel is not documentation about the language; it is the language, complete. PRINT, LET, INPUT, IF, GOTO, FOR, NEXT, GOSUB, RETURN, END, REM, and a shelf of operators and functions — twenty-five cards. If a word is not on a card, the machine cannot be told that thing: type 10 FROB A and it refuses before anything runs, naming the line and the word. This is the same shape as the collection's other first contact: the neighbours in First Contact can only say what their little grammar holds, and here you are on the other side of the glass — you hold the dictionary, and the machine is the one who can only mean what the words allow. Every programming language that has ever existed is this, at a bigger scale: a fixed vocabulary, a grammar for combining it, and a reader that obeys. Learn to see the dictionary and you have the master key to all of them.

Variables are boxes, and the watch panel is the point

A variable is a named box: LET C = C + 1 means "look in the box called C, add one, put the result back in C." Beginners are told this and nod, and then spend years being surprised by what is actually in the boxes. The bench removes the surprise by furniture: every box your program has ever filled sits on the right side of the screen with its current contents showing, updated the moment a statement changes it. Two rules of the house are visible there. A box nobody has filled reads as 0 — or "" if it is a word box (its name ends in $) — and a number box and a word box are different boxes even when their names match: the proof sets A = 5 and A$ = "FIVE" and prints them side by side as 5 FIVE. State is not a metaphor. It is a table, and the table is on the screen.

The lit line is the whole secret of debugging

Somewhere inside every computer is a program counter: a finger pointing at the statement being read. The bench paints that finger yellow. When a program misbehaves, there is no second secret to learn — the bug is always that the finger reached a line you did not expect, with boxes holding values you did not expect, and the craft of debugging is slowing the machine down until you can watch the exact step where expectation and reality part company. That is why the bench's slowest speed exists, and why the Step button executes exactly one statement. Run the guessing game slowly and watch line 70's test send the finger to line 100 instead of line 90: you have just seen an IF do its entire job. Everything a professional debugger shows you — breakpoints, watches, step-into — is this page's furniture, industrialised.

Loops are a counter, a test, and a jump — nothing else

A FOR loop feels like a single idea, but the machine reads it as three: put the start value in the counter box, and remember the end and the step; at NEXT, add the step, test against the end, and jump back if there is more to do. The bench keeps one honest quirk of its own here: the counter is tested before the first trip, so FOR I = 1 TO 0 does nothing at all (the proof prints only DONE). Some famous historical BASICs ran the body once before testing; this machine tests first, and says so in the dictionary. And under the FOR loop sits the older machinery it is made of — IF and GOTO can build any loop FOR can, which the Adding Machine example demonstrates with a GOTO-driven cycle that stops only when you type 0. Loops are not magic. They are a finger that sometimes jumps backwards.

Same text, same inputs, same seed — same run

The machine's dice are a seeded generator (mulberry32 — the same one Stack-a-Bot deals from). Every Run resets the seed to 12345, so a program that rolls the dice rolls the same dice, in the same order, forever: with seed 42, five draws of INT(RND * 1000) come out 601, 448, 852, 669, 174 — run it twice, get it twice; change the seed and the whole weather changes. This is not a limitation; it is the property that makes programs testable at all. A machine whose runs could not be repeated could never be proven right or wrong, only vibes-checked. The guessing game on the bench hides a 10 under the default seed, every time — which is why the mission checker can deal it fairly, and why you can rehearse against it. Determinism is the floor that all the collection's proof habits stand on.

The step budget is training wheels, and says so

Write 10 GOTO 10 on a real machine and it will obey you forever — the screen freezes, the fan spins, and the only cure is the plug. This machine counts statements instead, and at 100,000 it stops and tells you why. The proof runs the loop with a small budget of 5,000 and the machine halts at exactly 5,000 statements, neither one short nor one over; the shipped default is the full 100,000. It is a kindness real machines do not offer, and the page names it as one rather than letting you believe computers are naturally polite. Training wheels are honourable — as long as nobody paints them to look like the road.

How it's built — one machine, three drivers

The core is sealed, and everything drives the same one

Everything that decides what a program does — the tokenizer that reads characters into words, the parser that reads words into statements, the stepper that executes one statement and reports the machine's whole visible state — lives in one fenced block of pure code in the game file. It knows nothing about the page. The bench's Run and Step buttons drive it. The mission checker drives it, headlessly, with fixed inputs and the fixed seed. And the proof program lifts that exact block out of the shipped file and drives it too. There is no second implementation anywhere: the machine the proof interrogates is the machine you play, byte for byte.

The proof, in one paragraph

64 checks, all passing. The parser accepts every statement form in the dictionary and rejects — naming the line each time — an unknown word, a duplicate line number, a listing line with no number, an unterminated string, an IF with no line number after THEN, a FOR with no NEXT, and a jump to a line that does not exist. Known-answer programs print exactly what they must: the counting loop, the nested-FOR table (1 2 3 / 2 4 6 / 3 6 9), the STEP −1 countdown, a GOSUB routine nested two deep returning in the right order, string surgery ("AB" + "CD", LEN 4, ASC("A") = 65, CHR$(66) = "B", STR$ and VAL round-tripping), and the honest double — PRINT 0.1 + 0.2 gives 0.30000000000000004, because the machine's numbers are IEEE doubles and the page refuses to round your receipt. Stepping a program by hand, statement by statement, lands on byte-identical output and identical final boxes versus running it whole. The errors all name their lines: division by zero at line 30 (after printing OK at line 20), NEXT without FOR, RETURN without GOSUB, both directions of number-plus-word Type mismatch, MOD by zero, SQR of a negative, CHR$ out of range, and words typed into a number box at an INPUT.

The five examples, rehearsed

The shipped examples were run through the same core before the page was: Hello & Count ends in 13 steps, the Times Table in 23, the Star Triangle in 53, the Adding Machine totals 5 + 7 to THE TOTAL IS 12 in 14 steps, and the guessing game — fed a wrong guess of 1, then the 10 it was hiding — answers TOO LOW, then YOU GOT IT — GUESSES USED: 2, in 15 steps. If an example on the bench ever disagrees with this page, this page is the one that is wrong, and the proof is how we'd know.

The PRINT rule, exactly

Classic BASIC's spacing is folklore in most books; here it is a rule small enough to print. Items print left to right. A ; glues the next item directly on — except that a number printed before a ; wears one trailing space, so PRINT 1;2 gives 1 2 while PRINT "A";"B" gives AB. A , pads with spaces to the next multiple-of-14 column: PRINT 1,2 puts the 2 in column 14. Unless the statement ends with ; or ,, a newline follows; bare PRINT prints just the newline. The mission checker compares output line by line, ignoring trailing spaces and a final empty line — the one mercy it extends, and it is this sentence that grants it.

The missions, and what checking can and cannot prove

Each mission runs your program on the sealed core and compares output lines exactly. The reference solutions pass all four; a wrong-output program fails the first. And the checker is honest about its own limit, on the game page and here: it reads output, not code, so a program that simply PRINTs the expected lines passes missions 1–3 — the proof ran that cheat and watched it pass, all three. Mission 4 is guarded the cheap way that actually works: it is checked twice, with different inputs (7 and 8, then 100 and 250), and the proof's memorised PRINT 15 passes the first check and fails the second. Output-checking can prove what a program did; it cannot prove what the programmer learned. Those are different audits, and only one of them fits in a web page.

Simplifications, named

Stated plainly: the dialect is tiny by design — no arrays, no DATA/READ, no files, no graphics or sound, no string functions beyond the six on the cards, and IF … THEN takes a line number only, where real BASICs let a whole statement ride after THEN. Numbers are IEEE doubles: integers print exactly, but fractions carry the famous dust (0.1 + 0.2 above), very large results print in the machine's shorthand, and ^ of a negative base to a fractional power is refused rather than answered with a complex number. Three semantics were choices, and they are the machine's stated law, not BASIC's universal one: FOR tests its counter before the first trip (some classic BASICs test after); MOD follows INT's floor rule, so −5 MOD 3 = 1 where some machines answer −2; and AND/OR/NOT are logical tests on "not zero," not the bitwise operations some BASICs perform. INPUT is strict — a number box rejects words with an error, where many classic machines would shrug and store 0 — because a named refusal teaches more than a silent wrong answer. A line may hold several statements separated by :, and the stage lights the whole line while they run left to right within it. The step budget (100,000 statements) and the mission checker's output-only reading are named on the game page itself. Nothing else is simulated: the parser, the stepper, the dice, and the checker are the real machinery, running the real code, on this page.
